# Phase 10.1: capability auto-install - Context

**Gathered:** 2026-08-17
**Status:** Ready for planning

<domain>

## Phase Boundary

A shared, SessionStart-triggered mechanism that automatically grants
`capability install --scope user --yes` for a capability the first time it's needed —
no manual `capability install` command required. Applied to both capabilities that
exist today, `beads` (Phase 6) and `ponytail-everywhere` (Phase 10), and reused as-is by
`sota-numerics` (Phase 11) once planned. Must detect-and-re-grant, not grant-once: an
edit to a capability bundle after consent (or a fresh checkout/session) must be caught
and re-granted automatically, closing the silent-invalidation gap discovered debugging
Phase 10 (`.gsd-capabilities.json` consent record doesn't survive a bundle edit with any
visible warning today).

This reverses Phase 6's T-06-01 "do not build it" decision — that decision was never
actually put to the user (planner unilateral call, no CONTEXT.md, no AskUserQuestion
checkpoint) and was corrected 2026-08-17. See PROJECT.md Key Decisions table, the two
rows for PUB-03 / T-06-01.

</domain>

<decisions>

## Implementation Decisions

### Locked at roadmap level (not re-discussed)
- **D-00:** Scope is **user**, not project — explicitly re-decided by the user
  2026-08-17 (PROJECT.md Key Decisions), accepting the CB-3 tradeoff (auto-grant bypasses
  human bundle review) in exchange for zero-manual-step install. Not reopened in this
  discussion.

### Grant visibility
- **D-01:** SessionStart prints a one-line notice on every grant or re-grant
  ("Auto-installed capability: `<id>` (user scope)"), and prints nothing when the
  existing grant is already valid. Auto-install bypasses CB-3's human review; the notice
  is the only remaining trace that a grant happened, so it must fire every time state
  actually changes, not just once ever.

### Re-grant detection cadence
- **D-02:** The hash/validity check runs on **every SessionStart**, synchronously,
  before the session proceeds — same trigger point and same blocking pattern as the
  existing `bd prime` SessionStart hook in this repo. No lazy/first-use check: a phase
  must never dispatch against a capability that hasn't yet been validated this session.
- **D-03:** What gets hashed to detect drift is the **whole bundle directory**
  (`.gsd/capabilities/<id>/`, every file under it) — exactly the same scope gsd-core's
  own consent hash already uses. This matches the actual invalidation trigger documented
  in PROJECT.md's Key Decisions table (any file edit inside an already-consented bundle
  silently deactivates it today); hashing only `capability.json` would miss
  fragment/skill edits that gsd-core's own consent check still treats as invalidating.

### Auto-grant failure handling
- **D-04:** If the auto-grant call itself fails (`gsd-tools` missing, install command
  errors, etc.), print a **visible one-line warning**, then fail open — the capability
  simply stays inactive and the session/phase continues. This deliberately diverges from
  `bd`'s existing silent-fail-open convention: this path is now unattended (no human ever
  runs the install command by hand to notice a failure), so silence here means a
  capability can permanently never activate with nobody the wiser.

### Shared mechanism shape
- **D-05:** "Shared" means **vendored copies from one authored source**, not a shared
  runtime file. Each capability's own plugin (`beads`, `ponytail-everywhere`, and later
  `sota-numerics`) ships an identical copy of the auto-install script in its own
  `hooks/` directory — matching how `hooks/session-start.sh` already lives inside each
  plugin today. A true single shared runtime file was explicitly rejected: these are
  three separately-installable marketplace products (a user may install only one), so a
  cross-plugin file reference would break for any user who didn't install the plugin
  holding the shared copy. "Shared" therefore describes single authorship /
  drift-prevention (e.g. a lint/diff check across the vendored copies), not a shared
  file at install time.
- **D-06 (Claude's discretion):** Exact drift-prevention mechanism for keeping the
  vendored copies identical (e.g. a test that diffs the three files byte-for-byte, or a
  build step that copies from one canonical source into each plugin directory before
  release) is left to planning/implementation.

### Claude's Discretion
- Exact wording of the grant/re-grant notice and the failure warning beyond the
  one-line/fires-every-time constraints above (D-01, D-04).
- Exact hash algorithm and comparison mechanism for the bundle-directory check (D-03) —
  reuse whatever gsd-core's own consent hashing already uses if accessible, otherwise
  implement equivalent).
- Exact drift-prevention mechanism for vendored copies (D-06).
- How `sota-numerics` (Phase 11, not yet planned) wires in the vendored copy of this
  mechanism — Phase 11's own planning, not this phase's concern.

## Existing Code Insights

### Reusable Assets
- `hooks/session-start.sh` (in both `beads` and `ponytail` plugin dirs) — the file each
  vendored auto-install script variant gets added into or called from.
- gsd-core's own capability consent/hash implementation
  (`$HOME/.claude/gsd-core/bin/lib/capability-consent.cjs`,
  `capability-activation.cjs`, `capability-lifecycle.cjs`) — read before reimplementing
  hash/validity logic; reuse its exact hashing approach per D-03 rather than inventing a
  second one that could disagree with gsd-core's own invalidation trigger.

### Established Patterns
- Fail-open posture used throughout `beads`: `gates[].onError: "skip"`, missing/unreadable
  artifacts treated as absent, never as a hard stop. D-04 deliberately breaks from this
  pattern for the specific case of the auto-grant call failing — flag this divergence
  clearly in the plan so it isn't "fixed" back to silent by a future edit.
- `.gsd/capabilities/<id>/` directory-drop shape, `config` namespaced under `<id>.*` —
  same shape a vendored auto-install script must operate against for both `beads.*` and
  `ponytail.*`.

### Integration Points
- `hooks/hooks.json` in each of the two (soon three) plugins — SessionStart entry needs
  the auto-install check added alongside the existing `bd prime` / ponytail hook.
