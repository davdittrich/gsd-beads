## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-00:** Scope is **user**, not project — explicitly re-decided by the user
  2026-08-17 (PROJECT.md Key Decisions), accepting the CB-3 tradeoff (auto-grant bypasses
  human bundle review) in exchange for zero-manual-step install. Not reopened in this
  discussion.
- **D-01:** SessionStart prints a one-line notice on every grant or re-grant
  ("Auto-installed capability: `<id>` (user scope)"), and prints nothing when the
  existing grant is already valid. Auto-install bypasses CB-3's human review; the notice
  is the only remaining trace that a grant happened, so it must fire every time state
  actually changes, not just once ever.
- **D-02:** The hash/validity check runs on **every SessionStart**, synchronously,
  before the session proceeds — same trigger point and same blocking pattern as the
  existing `bd prime` SessionStart hook in this repo. No lazy/first-use check: a phase
  must never dispatch against a capability that hasn't yet been validated this session.
- **D-03:** What gets hashed to detect drift is the **whole bundle directory**
  (`.gsd/capabilities/<id>/`, every file under it) — exactly the same scope gsd-core's
  own consent hash already uses. This matches the actual invalidation trigger documented
  in PROJECT.md's Key Decisions table (any file edit inside an already-consented bundle
  silently deactivates it today); hashing only `capability.json` would miss
  fragment/skill edits that gsd-core's own consent check still treats as invalidating.
- **D-04:** If the auto-grant call itself fails (`gsd-tools` missing, install command
  errors, etc.), print a **visible one-line warning**, then fail open — the capability
  simply stays inactive and the session/phase continues. This deliberately diverges from
  `bd`'s existing silent-fail-open convention: this path is now unattended, so silence
  here means a capability can permanently never activate with nobody the wiser.
- **D-05:** "Shared" means **vendored copies from one authored source**, not a shared
  runtime file. Each capability's own plugin ships an identical copy of the auto-install
  script in its own `hooks/` directory. A true single shared runtime file was explicitly
  rejected: a cross-plugin file reference would break for any user who didn't install
  the plugin holding the shared copy.
- **D-06 (Claude's discretion):** Exact drift-prevention mechanism for keeping the
  vendored copies identical is left to planning/implementation.

## Summary

This phase adds a SessionStart-triggered auto-install for gsd-core's own capability
system (`beads`, `ponytail`), so a user who installs the `beads-lifecycle` or
`ponytail-everywhere` Claude Code plugin never has to hand-run
`gsd-tools capability install ... --yes`. The mechanism itself is small: gsd-core
already ships a fully-featured `capability install` CLI subcommand
(`node .../gsd-tools.cjs capability install <spec> --scope global --yes`) that is
idempotent, fail-closed on tampering, and safe to call repeatedly — the only new work is
(a) a cheap pre-check that avoids paying the full install-pipeline cost (staging, lock,
ledger rewrite) on every session when nothing changed, and (b) wiring that check into
each plugin's existing `SessionStart` hook alongside its current logic.

Two concrete, previously-undocumented gaps surfaced during this research and change the
shape of the plan:

1. **`ponytail-everywhere/` does not currently ship a `.gsd/capabilities/ponytail/`
   bundle at all.** Its existing `SessionStart` hook is a self-contained advisory banner
   that reads `.planning/config.json` directly and never calls `capability install`. The
   `.gsd/capabilities/ponytail/` bundle (with its `steps`/`contributions`/`gates` wiring
   into gsd-core's own plan/execute/verify lifecycle) exists only at the **repo root**
   (this repo's own dev/dogfood copy) — not inside `ponytail-everywhere/`, the actual
   shipping plugin directory. This phase must vendor that bundle into
   `ponytail-everywhere/.gsd/capabilities/ponytail/` before an auto-install call there
   has anything to install.

2. **The GitHub Release zip and the marketplace/plugin-install cache are two different
   distribution paths with different contents**, and only one of them carries
   `.gsd/capabilities/beads/`. `.github/workflows/release.yml`'s allowlist
   (`.claude-plugin`, `hooks`, `.agents/skills`, `README.md`, `LICENSE`) omits
   `.gsd/`. But the **documented, primary install path** (`claude plugin marketplace add`
   + `claude plugin install`) clones the whole repository into
   `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` — verified live against
   this machine's own cache at `~/.claude/plugins/cache/gsd-beads/beads-lifecycle/1.2.0/`,
   which **does** contain `.gsd/capabilities/beads/capability.json` intact. So the
   documented install path already works for `beads`; the release-zip gap is real but
   secondary. `ponytail-everywhere` has no equivalent cache artifact to inspect (never
   installed via the marketplace flow with the new bundle), so gap #1 must be closed
   before this can be verified for it too.

**Primary recommendation:** Author one vendored bash script (e.g. `capability-auto-install.sh`)
that (1) computes a cheap whole-bundle-directory hash of `$CLAUDE_PLUGIN_ROOT/.gsd/capabilities/<id>`
using stdlib tools only (`find` + `sha256sum`, no new dependency), (2) compares it to a
small sidecar state file the script itself owns (not gsd-core's ledger), (3) on
mismatch/absence calls `gsd-tools capability install "$CLAUDE_PLUGIN_ROOT/.gsd/capabilities/<id>" --scope global --yes`
and prints the D-01 notice, (4) on install failure prints the D-04 warning and exits 0
(fail open), (5) on hash match, does nothing and exits 0 silently. Vendor identical copies
into `hooks/` (root, for `beads`) and `ponytail-everywhere/hooks/` (for `ponytail`, after
also vendoring its `.gsd/capabilities/ponytail/` bundle), invoked from each plugin's
existing `session-start.sh` alongside (not replacing) what is already there.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| SessionStart auto-install trigger | Claude Code plugin hook (bash, runs in the end user's Claude Code process) | — | `hooks.json`'s `SessionStart` entry is the only trigger point that fires before a session/phase can dispatch against the capability (D-02); this is a host-process hook, not application code. |
| Drift detection (bundle hash) | Plugin hook script (bash, stdlib) | gsd-core internal (`capability-consent.cjs`'s `bundleContentHash`, optionally reused) | Must run every session with near-zero cost (D-02); a full Node `require()` of gsd-core internals is possible but couples the vendored script to a private API — a shell-only hash (`find`+`sha256sum`) is safer and equally sufficient for D-03's "whole bundle directory" scope. |
| Capability install/promote/ledger-write | gsd-core CLI (`gsd-tools.cjs capability install`, Node.js) | — | Already fully implemented (staging, atomic promote, ledger commit, first-party-id collision guard); the auto-install script must call it, never reimplement it. |
| Consent binding | gsd-core CLI (`capability-lifecycle.cjs`'s `bindProjectConsent`) | — | Only fires for `--scope project`; **global scope explicitly records nothing and needs no consent** (`shouldBindConsent` returns `false` for `scope !== 'project'`) — this is why D-00's "user scope" choice is what makes unattended `--yes` auto-grant safe: there is no repo-plantable ledger to spoof at global scope, since the ledger lives under the user's own home directory. |
| Bundle content (capability.json, fragments, skills) | Plugin release artifact (git-tracked files inside each plugin's own directory tree) | — | Must be vendored inside each plugin's own root so `$CLAUDE_PLUGIN_ROOT`-relative resolution works regardless of which plugin was installed (D-05); a cross-plugin reference would break for a user who installed only one plugin. |

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Shell-only `find`+`sha256sum` hash | `require()` gsd-core's own `bundleContentHash` directly (mirroring how `gsd-tools.sh` already locates and shells into `gsd-tools.cjs`) | Byte-identical to gsd-core's own invalidation semantics (D-03's stated preference), but couples the vendored script to a **private, unexported** gsd-core internal module (`capability-consent.cjs` is documented as a "LEAF MODULE" for gsd-core's own internal use, not a stable CLI surface) — a future gsd-core refactor could rename/move it with no deprecation warning, silently breaking three vendored copies across two-then-three plugins. | Hash-then-conditionally-install | Unconditionally call `capability install ... --yes` every SessionStart, let its own idempotent-reinstall logic be the "check" | Simpler (one code path, no sidecar state file to design/own) but pays the full install-pipeline cost (lock acquire, staging, promote-with-backup, ledger rewrite) on **every** session even when nothing changed — directly conflicts with D-02's "without meaningfully slowing session start" and D-01's "prints nothing when the existing grant is already valid" (a full reinstall always mutates `updatedAt`, so distinguishing "no-op" from "re-grant" for the notice would require inspecting its own before/after state anyway — no simpler than a pre-hash). |

### Pattern 1: Idempotent capability install as the re-grant primitive

**What:** Every re-grant — first install, or re-install after drift — is the exact same
CLI call: `gsd-tools capability install "$SPEC" --scope global --yes`. There is no
separate "upgrade" vs "install" branch for the auto-install script to reason about;
`installCapability()` in gsd-core already treats "bundle dir already exists" as an
upgrade-like reinstall internally (backs up the old dir, promotes the new, rewrites the
ledger) — see `capability-lifecycle.cjs:774-952`, specifically `isUpgradeLike` at line
884.
**When to use:** Any time the pre-check's hash comparison says "different or absent."
**Example:**
```bash
# Source: /home/dd/.claude/gsd-core/bin/lib/capability-command-router.cjs:263-296
# (CLI comment documents the exact flag surface this call uses)
gsd_tools capability install "${CLAUDE_PLUGIN_ROOT}/.gsd/capabilities/${CAP_ID}" \
  --scope global --yes
```

### Pattern 2: Absolute, `$CLAUDE_PLUGIN_ROOT`-rooted spec path — never a relative one

**What:** `capability-source.cjs`'s local-path resolver does
`path.resolve(parsed.target)`, which resolves a relative spec (`./...`, `../...`)
against **`process.cwd()`** at the time `gsd-tools` runs — not against the plugin's own
directory. At SessionStart, `cwd` is the **end user's project root**, not the plugin
install location. `[VERIFIED: /home/dd/.claude/gsd-core/bin/lib/capability-source.cjs:704-724]`
The existing ledger entry in this very repo shows the failure mode already latent: its
`source` field is the bare relative string `"./.gsd/capabilities/ponytail"`
`[VERIFIED: /home/dd/projects/gsd-beads/.gsd-capabilities.json:8]`, which only resolved
correctly because the install command happened to be run with `cwd` == the repo root by
coincidence (Phase 10's dev/dogfood install, not the auto-install path this phase adds).
**When to use:** Always — build the spec as `"${CLAUDE_PLUGIN_ROOT}/.gsd/capabilities/${CAP_ID}"`,
never a bare relative path, in the vendored script.
**Example:**
```bash
# WRONG — resolves against the end user's project cwd, not the plugin:
gsd_tools capability install "./.gsd/capabilities/beads" --scope global --yes

# RIGHT — absolute, rooted at the plugin's own install location:
gsd_tools capability install "${CLAUDE_PLUGIN_ROOT}/.gsd/capabilities/beads" --scope global --yes
```

### Pattern 3: `--scope global` is the CLI's actual name for "user scope" — no `--scope user` flag exists

**What:** The CLI's `--scope` flag accepts exactly two values, `global` and `project`
— never `user`. `capResolveScope` maps `global` → `runtimeDir = process.env.GSD_HOME ||
os.homedir()`, i.e. the user's own home directory, which is what CONTEXT.md/ROADMAP.md
mean by "user scope."
`[VERIFIED: /home/dd/.claude/gsd-core/bin/lib/capability-command-router.cjs:69-76]`
The phase goal text and ROADMAP.md both literally say `capability install --scope user --yes`
— **this exact invocation does not exist and will fail CLI arg validation**
(`error('Invalid --scope "user": expected global or project', ...)`). This is almost
certainly informal phase-goal prose, not a literal command to transcribe — flag this
explicitly for the plan so no task ships `--scope user` verbatim.
**When to use:** Always write `--scope global` in code; reserve "user scope" for prose/docs only.

### Anti-Patterns to Avoid

- **Re-implementing the ledger or consent schema inside the vendored script:** gsd-core
  owns `.gsd-capabilities.json`'s shape and `~/.gsd/consent.json`'s content-hash binding
  end to end (`capability-ledger.cjs`, `capability-consent.cjs`). The vendored script's
  job is strictly "decide whether to call `capability install`," never to hand-write
  ledger entries.
- **Storing the pre-check's cached hash inside `.gsd-capabilities.json` itself:** that
  file's `integrity` field is gsd-core-owned and is presently `""` for every local-path
  install (`integrity pinning is not supported for local sources`,
  `[VERIFIED: /home/dd/.claude/gsd-core/bin/lib/capability-source.cjs:709-711]`) — writing
  into it from outside the lifecycle module risks a future gsd-core release overwriting
  or misinterpreting the field. Use a separate, script-owned sidecar file instead (D-06
  is explicitly Claude's discretion on this).
- **Skipping the `$CLAUDE_PLUGIN_ROOT` fallback pattern already established in this
  repo's hooks:** every existing hook (`hooks/session-start.sh`,
  `ponytail-everywhere/hooks/session-start.sh`, `ponytail-everywhere/hooks/gsd-tools.sh`)
  falls back to `$(cd "$(dirname "$0")/.." && pwd)` when `CLAUDE_PLUGIN_ROOT` is unset
  (covers a bare git checkout with no `/plugin install` ever run — see PROJECT.md Key
  Decisions row "A merely checked-out gsd-beads repo... does not auto-load
  `hooks/hooks.json`" and the existing `test-session-start.sh` Case 10, which asserts
  byte-identical output with/without the env var). The new script must follow the same
  fallback or it silently breaks bare-checkout dev sessions.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Capability install/promote/ledger-write | A custom directory-copy + JSON-ledger-editor | `gsd-tools capability install <spec> --scope global --yes` | Already atomic (stage → validated-promote → ledger commit), already handles a stale ledger, crash-mid-install recovery (`reconcileCapabilities`), and first-party-id collision refusal. `[VERIFIED: capability-lifecycle.cjs:770-952]` |
| Whole-bundle content hashing to gsd-core's exact semantics | A from-scratch canonical hash if byte-exact parity with gsd-core's own invalidation trigger is required | `bundleContentHash()` from `capability-consent.cjs` if you choose the "reuse gsd-core's own hashing" branch of D-03's discretion — it is deliberately length-framed, raw-byte, symlink-refusing, and DoS-bounded; a hand-rolled shell hash (`find`+`sha256sum`) is *not* byte-identical to it (different serialization, different treatment of empty directories, symlinks, non-UTF8 names) but is sufficient for THIS use case's actual need (detect "something in the bundle changed"), not for security-grade tamper-binding (which global scope doesn't require — no consent record is bound at global scope in the first place). | Don't confuse "detect drift for a UX notice" with "cryptographically bind consent" — they have different correctness bars. gsd-core's own consent binding only exists for `--scope project`; global scope is trusted by design (`shouldBindConsent` returns false), so the auto-install pre-check only needs to avoid *unnecessary* reinstalls, not defeat a hostile actor. |

**Key insight:** The temptation in this phase is to treat "detect-and-re-grant" as a
security mechanism needing the same rigor as gsd-core's `#1459` consent-hash work. It
isn't — global/"user" scope is explicitly the trusted-without-a-record scope in
gsd-core's own model. The re-grant check exists purely to (a) satisfy D-02's "never
dispatch against unvalidated state" liveness requirement and (b) avoid silent
degradation (D-01's notice requirement), not to close a security gap.

## Common Pitfalls

### Pitfall 1: Treating "capability install --scope user" from the phase goal as literal CLI syntax

**What goes wrong:** A task literally shells out `gsd-tools capability install <spec> --scope user --yes`; the CLI's arg validator rejects `user` (`Invalid --scope "user": expected global or project`), the install silently fails, and — per D-04 — this then correctly prints a warning and fails open, but the capability NEVER activates for any user, forever, with the failure looking like an environment problem rather than a typo.
**Why it happens:** ROADMAP.md's own Phase 10.1 goal text and PROJECT.md's Key Decisions
table both say "scope user" in prose, mirroring the CLI's actual `global` value only in
spirit.
**How to avoid:** Use `--scope global` in all code; the plan/tasks should state this
translation explicitly rather than transcribing the roadmap prose.
**Warning signs:** Any grep for `--scope user` inside a shell script in this repo should
return zero results.

### Pitfall 2: Full reinstall on every SessionStart defeats D-02's performance intent

**What goes wrong:** The auto-install script unconditionally calls `capability install`
every session "to be safe," skipping the hash pre-check. `installCapability()` always
acquires a cross-process lock, stages a full copy of the bundle, and rewrites the ledger
— even when nothing changed — adding a Node.js process spawn plus filesystem I/O to
every single session start for every installed capability (multiplied by however many
capabilities Phase 11 adds).
**Why it happens:** It's the simplest correct implementation and the temptation from
Pattern 1 above ("it's idempotent, so just always call it") is real.
**How to avoid:** Gate the `capability install` call behind the cheap
directory-hash comparison (D-03); only pay the full install cost when the hash actually
changed or no prior grant exists.
**Warning signs:** SessionStart latency measurably increases after this phase ships, or
`ls ~/.gsd-capabilities.json`'s `updatedAt` timestamp changes on every session even when
the bundle content is byte-identical to the prior session.

### Pitfall 3: Auto-install script assumes it runs from inside the plugin directory

**What goes wrong:** A script written and tested by `cd`-ing into
`ponytail-everywhere/` and running `./hooks/capability-auto-install.sh` directly (as a
developer naturally would) works fine there, but breaks the moment `hooks.json` invokes
it via `bash "${CLAUDE_PLUGIN_ROOT}/hooks/capability-auto-install.sh"` from the end
user's project directory as `cwd` — any relative path inside the script (spec path,
sidecar state file path) silently resolves against the wrong directory.
**Why it happens:** Pattern 2 above, generalized — this is the SAME class of bug the
existing ledger entry's `"./.gsd/capabilities/ponytail"` source string already
demonstrates happened once in this exact codebase.
**How to avoid:** Root every path off `$CLAUDE_PLUGIN_ROOT` (with the existing
dirname-of-`$0` fallback pattern), never off a bare relative path or an assumed `cwd`.
**Warning signs:** The existing `test-session-start.sh` Case 10 pattern (byte-identical
output whether `CLAUDE_PLUGIN_ROOT` is set or derived from `$0`) is exactly the kind of
test this new script needs; absence of an equivalent test is itself a warning sign.

### Pitfall 4: Sidecar hash-cache file collides across the two/three vendored copies

**What goes wrong:** If the sidecar state file that caches "last known bundle hash" uses
a fixed filename not keyed by capability id (e.g. `~/.gsd/auto-install-hash`), the
`beads` copy and the `ponytail` copy (and later `sota-numerics`) stomp on each other's
cached hash, causing spurious re-installs or spurious silence.
**Why it happens:** D-05's "vendored, not shared" design means three independent copies
of the SAME script logic will each want to persist state; if they're not each keyed by
capability id (or written to per-id file paths) they collide.
**How to avoid:** Key the sidecar state by capability id — either one JSON file with a
per-id key (`{"beads": "<hash>", "ponytail": "<hash>"}`) or per-id files
(`~/.gsd/<id>-auto-install.hash`). Since three separately-installable plugins might all
try to write the SAME shared-JSON sidecar concurrently (a user could have all three
installed), prefer per-id files (no read-modify-write race) unless a locking pattern is
already justified elsewhere.
**Warning signs:** Installing both `beads-lifecycle` and `ponytail-everywhere` and
observing one capability's re-grant notice fire on every session (its cached hash keeps
getting overwritten by the other capability's check).

### Reading gsd-tools' own path-resolution fallback chain (already proven in this repo)

```bash
# Source: /home/dd/projects/gsd-beads/ponytail-everywhere/hooks/gsd-tools.sh (verified, lines 1-18)
gsd_tools() {
  if [ -z "${_GSD_TOOLS_ARGS_SET+x}" ]; then
    _GSD_TOOLS_ARGS_SET=1
    local _root
    _root="$(git rev-parse --show-toplevel 2>/dev/null)"
    if [ -n "$_root" ] && [ -f "$_root/gsd-core/bin/gsd-tools.cjs" ]; then
      _GSD_TOOLS_ARGS=(node "$_root/gsd-core/bin/gsd-tools.cjs")
    elif command -v gsd-tools >/dev/null 2>&1; then
      _GSD_TOOLS_ARGS=(gsd-tools)
    elif [ -f "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/gsd-core/bin/gsd-tools.cjs" ]; then
      _GSD_TOOLS_ARGS=(node "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/gsd-core/bin/gsd-tools.cjs")
    else
      _GSD_TOOLS_ARGS=()
    fi
  fi
  [ "${#_GSD_TOOLS_ARGS[@]}" -gt 0 ] || return 127
  "${_GSD_TOOLS_ARGS[@]}" "$@"
}
```

D-04 failure path should treat identically to an install-command failure (print warning,

## Open Questions

1. **Does the planner want the pre-check hash sidecar to live under `~/.gsd/` (alongside
   gsd-core's own `~/.gsd/consent.json`) or under a plugin-specific location (e.g.
   `~/.claude/plugins/...`)?**
   - What we know: `~/.gsd/consent.json` is gsd-core's own user-owned store path
     (`consentStorePath` = `(GSD_HOME||homedir())/.gsd/consent.json`); a sidecar under
     the same `~/.gsd/` directory is a natural, discoverable neighbor.
   - What's unclear: whether writing into `~/.gsd/` from a THIRD-PARTY vendored script
     (not gsd-core itself) is acceptable given that directory is otherwise exclusively
     gsd-core's own — no explicit prohibition found, but no precedent for a plugin
     writing there either.
   - Recommendation: use `~/.gsd/` for consistency (it is already the established
     "gsd-core's user-home state" location) but name the file distinctly (e.g.
     `~/.gsd/capability-auto-install-state.json`) so a future gsd-core release cannot
     collide with it.

2. **Should the D-06 drift-prevention check (keeping the vendored script copies
   identical across plugins) be a CI check, a pre-commit hook, or a manual `diff`
   discipline documented in a comment?**
   - What we know: this repo already has `.github/workflows/release.yml`; adding a CI
     step (`diff hooks/capability-auto-install.sh ponytail-everywhere/hooks/capability-auto-install.sh`)
     is a small, cheap addition to an existing pattern.
   - What's unclear: whether the user wants this enforced in CI now or deferred as a
     documented convention, given D-06 was explicitly left to planning discretion.
   - Recommendation: a CI diff-check is the lazy, durable choice — it costs one workflow
     step and cannot silently drift, versus a comment-only convention that depends on
     every future editor remembering to update both copies by hand.
