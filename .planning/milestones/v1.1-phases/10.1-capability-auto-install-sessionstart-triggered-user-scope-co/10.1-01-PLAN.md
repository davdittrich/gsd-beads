<assumption_delta_decision>
**promote** — the SessionStart auto-install becomes the primary way `beads` and `ponytail`
capabilities get granted. The hand-run `gsd-tools capability install` command is demoted to
a fallback/troubleshooting detail, not a parallel supported path. Rationale: keeping both as
first-class paths would mean two consent stories for the same capability, which is exactly
the ambiguity D-00 resolved by accepting the CB-3 tradeoff at global scope.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Claude Code host process → hook script | The plugin's bash hook runs unattended, with the end user's privileges, on every session start. |
| Hook script → gsd-core CLI | The script supplies `--yes`, suppressing the interactive executable-surface disclosure that a human would otherwise read. |
| Plugin bundle files → user's global capability ledger | Bundle content under `$CLAUDE_PLUGIN_ROOT/.gsd/capabilities/<id>/` becomes active capability code after an unattended install. |
| Local filesystem (`$HOME/.gsd/`) → hook script | The sidecar hash file is read to decide whether to skip the install. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10.1-01 | Elevation of Privilege | `capability-auto-install.sh` passing `--yes` to `capability install` | high | accept | This is the CB-3 tradeoff the user explicitly re-decided on 2026-08-17 (D-00). gsd-core's own `evaluateInstallTrust` / `discloseExecutableSurfaces` still execute inside `installCapability()`; `--yes` only suppresses the interactive prompt, it does not bypass validation. Accepted at global scope, which gsd-core designates trusted-without-a-consent-record (`shouldBindConsent` returns false for non-project scope). Documented in the phase SUMMARY, not silently absorbed. |
| T-10.1-02 | Tampering | Relative spec path resolving against the end user's cwd | high | mitigate | Build the spec as the absolute `"$PLUGIN_ROOT/.gsd/capabilities/$CAP_ID"`. A relative spec would resolve against the end user's project root, letting an attacker-controlled `./.gsd/capabilities/<id>/` in any repo the user opens be installed globally. Enforced by the Task 1 acceptance criterion asserting the stub received an absolute path, and by the Task 2 plugin-root parity case. |
| T-10.1-03 | Tampering | Sidecar hash file at `${GSD_HOME:-$HOME}/.gsd/capability-auto-install-<id>.hash` | low | accept | A pre-planted matching hash suppresses the re-grant and the D-01 notice. Same-user local tampering is inside the existing single-user trust boundary that `~/.gsd/consent.json` already lives in and that gsd-core itself does not defend against. Written with default umask, no world-writable mode. |
| T-10.1-04 | Denial of Service | Unconditional reinstall on every session | medium | mitigate | Gate the install behind the cheap directory hash (D-03) so the common path spawns no `node` process; asserted by the "unchanged rerun invokes install zero times" criterion. |
| T-10.1-05 | Repudiation / Information Disclosure | Silent install failure | medium | mitigate | D-04: a visible one-line stderr warning on every failure, distinguishing "no gsd-tools" from "install failed", and no state-file write so the next session retries. Asserted by Task 2 cases 1–2. |
| T-10.1-06 | Spoofing | Capability id used to build filesystem paths | low | mitigate | Validate `$1` against gsd-core's own `^[a-z][a-z0-9-]*$` identifier shape before it reaches any path construction; exit 0 silently otherwise (ASVS V5, defense in depth — call sites pass only hard-coded literals). |
| T-10.1-SC | Tampering | npm/pip/cargo installs | n/a | accept | No package-manager install occurs in this phase; RESEARCH.md's Package Legitimacy Audit records "not applicable — zero external packages". |
</threat_model>
