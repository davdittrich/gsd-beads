# Phase 11.1: Code Review Report

**Reviewed:** 2026-08-17T13:08:01Z
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

Reviewed the `beads.enabled` default-flip (false → true) across `capability.json`, the four
beads-skill Step 1 config gates, and the doc set (README, both `PRIME.md` twins, the PRD, and the
new `CHANGELOG.md`).

The core change is sound: `capability.json`'s `beads.enabled.default` is `true`, matches
`version: 0.2.0`, and all four `SKILL.md` Step 1 blocks (`beads-recall`, `beads-sync`,
`beads-status`, `beads-migrate-todos`) carry byte-identical inverted gate logic (diffed directly —
confirmed identical) that stops only on an explicit `config.beads.enabled === false` and falls
through to the shipped default otherwise. Docs (`README.md`, both `PRIME.md` twins,
`docs/prd-beads-capability.md`'s manifest snippet, `CHANGELOG.md`) all state the `true` default
consistently.

Two issues found, both pre-existing content this phase's edits sit adjacent to but did not
introduce or fix: a wrong skill name in `beads-migrate-todos`'s disabled message, and a
type-strictness gap in the new gate condition that silently fails open (keeps beads enabled) on a
malformed `enabled` value instead of disabling. Two minor doc-drift notes are informational only.

## Warnings

### WR-01: `beads-migrate-todos` disabled message names the wrong skill

**File:** `.gsd/capabilities/beads/skills/beads-migrate-todos/SKILL.md:35`
**Issue:** The Step 1 disabled message for `beads-migrate-todos` reads:

```text
GSD > MIGRATE TODOS

Beads sync is disabled (beads.enabled).
Nothing was migrated; no todo files were touched.
```

The other three skills each name themselves correctly ("Beads recall is disabled...", "Beads
sync is disabled..." in `beads-sync`, "Beads status is disabled..."). `beads-migrate-todos`
copies `beads-sync`'s wording verbatim, so a user who disables `beads.enabled` and then runs
`/gsd-migrate-todos` sees a message claiming "sync" is disabled rather than migration — misleading
when the two are triggered independently. This line predates this phase (commit `e4ac490` only
touched Step 1's condition text, not the disabled-message body), but it sits inside a file this
phase edited and is still wrong in the shipped result.
**Fix:**
```diff
-Beads sync is disabled (beads.enabled).
+Beads migrate-todos is disabled (beads.enabled).
 Nothing was migrated; no todo files were touched.
```

### WR-02: Opt-out gate fails open on a non-boolean `enabled` value

**File:** `.gsd/capabilities/beads/skills/beads-recall/SKILL.md:27` (identical text at
`beads-sync/SKILL.md:27`, `beads-status/SKILL.md:27`, `beads-migrate-todos/SKILL.md:27`)
**Issue:** All four skills gate on: "`config.beads.enabled` is explicitly the boolean `false`" to
disable, "Otherwise ... fall through" to enabled. The schema in `capability.json` declares
`beads.enabled` as `type: boolean`, but nothing enforces that at the config-file level — a user
opting out with `"beads.enabled": "false"` (string) or `0` or `null` no longer matches "explicitly
the boolean `false`" and silently falls through to the enabled default. Before this phase, the
opt-in condition was `config.beads.enabled !== true`, which treated *any* non-`true` value
(including a typo'd string) as disabled — fail-closed with respect to the feature staying off.
The new condition inverts that safety: a malformed opt-out attempt now silently keeps the
integration running rather than disabling it, which is the direction most likely to surprise a
user who explicitly tried to turn it off. This is consistent across all four skills (a systemic
design choice, not a one-off slip), but it's the exact edge case an opt-out mechanism should
fail safe on.
**Fix:** Broaden the stop condition to catch any falsy/non-`true` explicit value, e.g.: "If the
file exists, `config.beads` is present, and `config.beads.enabled` is present and is not the
boolean `true`: display the disabled message and STOP." This keeps the "absent key → shipped
default" fallthrough intact while restoring fail-closed behavior for a malformed explicit value.

## Info

### IN-01: PRD's illustrative manifest snippet still shows `"version": "0.1.0"`

**File:** `docs/prd-beads-capability.md:138`
**Issue:** This phase bumped the real `capability.json` to `version: 0.2.0` (commit `252984f`)
and correctly updated the PRD's `beads.enabled` default on line 148 of the same illustrative JSON
block (commit `7e9053b`), but left `"version": "0.1.0"` on line 138 of that same snippet
untouched — now inconsistent with the shipped manifest it's meant to illustrate. The PRD is
explicitly a draft design document (already diverged from the implementation in other ways: its
skills list omits `beads-migrate-todos`, its config schema includes a `beads.recall_scope` key
absent from the real `capability.json`, and it lists a `ship:post` step the real manifest doesn't
have), and commit `7e9053b`'s own message notes "sibling config entries ... untouched" as a
deliberate scope boundary, so this is not a regression this phase should have fixed. Noted for
completeness since it is a version-number/code inconsistency in a file this phase touched.
**Fix:** Out of this phase's scope; if the PRD is kept as a living reference rather than a frozen
historical draft, a follow-up pass should reconcile its manifest snippet with the current
`capability.json` wholesale rather than patching individual fields piecemeal.

### IN-02: Step 1's "Otherwise" enumeration omits the explicit-`true` case

**File:** `.gsd/capabilities/beads/skills/beads-recall/SKILL.md:28` (identical text replicated in
the other three `SKILL.md` files)
**Issue:** Step 1.3 spells out three sub-cases folded into "Otherwise": file missing, `config.beads`
absent, or `config.beads` present with no `enabled` key. It doesn't explicitly list the case where
`config.beads.enabled` is present and explicitly `true` — that case is logically covered by
"Otherwise" (only the explicit-`false` condition in step 2 stops), but the enumerated list reads
as if it's meant to be exhaustive of the fallthrough cases and isn't. Purely a readability gap;
behavior is correct.
**Fix:** Append ", or `config.beads.enabled` is explicitly `true`" to the enumerated list for
completeness, or replace the enumeration with a plain "any case other than an explicit `false`."
