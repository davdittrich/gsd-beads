<assumption_delta_decision>
The assumption-delta scan fired on this phase (`kind: pluralization`). The underlying transition is
real: `bd` moves from *one of two* places task content lives to *the* place it lives.

**Decision for this plan: promote, do not add alongside.** `_task_description` is the single
renderer for task content into `bd` — there is deliberately no second formatter, no per-call-site
override, and no configurable shape. The one place that writes the shape is the one place a future
change edits, matching `_todo_description`/`_write_report`'s existing discipline in this capability.
The `acceptance_criteria` split into bd's own structured field is not a second renderer; it is one
field routed to the structured flag bd already provides for it, verified live.
</assumption_delta_decision>

## Alternatives Considered

**1. Acceptance criteria: bd's `--acceptance` structured field vs. folding into the `-d` blob vs. `--notes`.**
`bd create --help` on this machine (checked 2026-08-19) offers `-d/--description`,
`--acceptance`, `--notes` and `--design` as separate flags, and 16-RESEARCH.md's scratch-database
round trip confirms `bd show --json` returns `description` and `acceptance_criteria` as distinct
top-level keys. Folding criteria into `-d` (the `_todo_description` precedent, which does exactly
that for `files:` because bd has no structured field for it) would be marginally fewer lines, and
`--notes` would work as a dumping ground. **Decided on ecosystem support** (rank 3): using bd's own
first-class field keeps acceptance criteria machine-queryable by every `bd` consumer instead of
buried in markdown prose, at a cost of two argv elements. `files` still rides in `-d`, unchanged,
precisely because bd has no structured field for it.

**2. Passing description content: `-d <string>` argv vs. `--body-file` / `--stdin`.**
Both alternatives exist on `bd create --help` (checked 2026-08-19). `--body-file` would sidestep
any argv length ceiling for a very large task body. **Decided on simplicity/LOC** (rank 2): `-d`
is one appended list element with no temporary file, no cleanup path, and no new failure mode,
and PLAN.md task bodies at this project's scale are a few KB. The ceiling is recorded as T-16-03
in the threat register with `--body-file` named as the upgrade path if it is ever hit.

**3. Milestone epic description source: ROADMAP `## Milestones` bullet vs. plan `<objective>` vs. leaving it title-only.**
`.planning/ROADMAP.md` (read 2026-08-19) carries one verbatim bullet per milestone under
`## Milestones`. Reusing the triggering plan's `<objective>` would be zero new code but describes
one phase, not the milestone that spans many. Leaving it title-only would be zero code but
contradicts D-06's explicit naming of the milestone epic resolver. **Decided on maintenance
overhead** (rank 4): reading the existing bullet verbatim clones `get_phase_header`'s established
no-translation pattern, so there is exactly one authored source of milestone prose and no second
copy to drift.
