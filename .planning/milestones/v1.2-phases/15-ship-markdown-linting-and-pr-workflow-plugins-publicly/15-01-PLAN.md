<plan_decisions>
Resolving the open question 15-PATTERNS.md explicitly flagged for planner resolution (where the new
plugin manifest's `skills` array should point), plus the two wrapper-shape calls it left implicit.
These bind Plan 02 as well.

- **PD-01 — `plugin.json` carries NO `skills` key.** Evidence, not preference: the two plugins Phase
  12 extracted shipped manifests with exactly five keys (`name`, `version`, `description`, `author`,
  `license`) and no `skills` key, and both passed `claude plugin validate . --strict`. Recover them
  with `git show 52b53d2^:ponytail-everywhere/.claude-plugin/plugin.json` and
  `git show 52b53d2^:sota-numerics/.claude-plugin/plugin.json`. Those are exact structural analogs:
  capability-only plugins whose payload is a `.gsd/capabilities/<id>/` bundle plus a SessionStart
  hook. `beads-lifecycle`'s `"skills": ["./.agents/skills/beads"]` is NOT a counterexample — it
  points at a Claude Code skill directory, and that plugin's four gsd-core *capability* skills under
  `.gsd/capabilities/beads/skills/` are deliberately absent from that array. `markdown-linting-report`
  is a capability skill: it is already declared in `capability.json`'s `"skills": ["markdown-linting-report"]`
  and is resolved from inside the bundle by `gsd_tools capability install`. Listing it again in the
  plugin manifest would either duplicate or shadow that registration. It is therefore omitted, and no
  file is relocated to `.agents/skills/`.
- **PD-02 — vendor `capability-auto-install.sh` from `plugins/beads-lifecycle/`, byte-identical, as
  the only supporting script.** That copy inlines its own `gsd_tools()` resolver, so this plugin needs
  no `hooks/gsd-tools.sh` — a deliberate divergence from `ponytail-everywhere`'s two-file split, and
  the laziest tree that still satisfies Phase 10.1 D-05's vendored-copy-per-plugin rule.
- **PD-03 — `session-start.sh` is `beads-lifecycle`'s minus its beads-specific halves:** no
  `.beads/PRIME.md` self-heal, no `exec bd prime --hook-json`. What remains is the `PLUGIN_ROOT`
  resolution line and one call to the vendored script with this capability's id.
</plan_decisions>

## Alternatives Considered

- **Construct a minimal plugin-tree wrapper around the existing bundle, then `cp` to a scratch dir +
  fresh `git init` + `gh repo create --source=. --push`**: adds the four files a Claude Code plugin
  root requires (`.claude-plugin/plugin.json` plus a `hooks/` SessionStart wrapper) and publishes from
  current file state with no history machinery.
  `https://code.claude.com/docs/en/plugins-reference` (2026) documents `.claude-plugin/plugin.json` at
  the repo root as the only hard requirement, and `gh repo create --help` (gh 2.97.0, verified on this
  machine, 2026) documents `--source` as the existing-local-repo path.
- **Ship the capability bundle with no `hooks/` wrapper at all** — a plugin whose payload is only
  `.gsd/capabilities/markdown-linting/`. Strictly fewer files, and `capability.json` already declares
  `"hooks": []`. Ruled out on correctness, not size: without a SessionStart hook nothing calls
  `gsd_tools capability install`, so the capability is never granted, the `verify:post` step never
  fires, and ROADMAP success criterion 3 ("each capability auto-installs/re-consents") fails by
  construction. Evidence: `plugins/beads-lifecycle/hooks/session-start.sh` and the Phase 10.1 D-05
  vendoring decision (2026).
- **`git subtree split -P .gsd/capabilities/markdown-linting -b <branch>` then push that branch**:
  rewrites the bundle's commits into a synthetic branch whose root is the bundle, preserving Phase 13
  history. `git subtree --help` (git 2.55.0, verified on this machine, 2026). Ruled out by D-00's
  locked "fresh init, no history extraction", and it would in any case produce a root that is the
  bundle rather than the plugin root a marketplace install needs.

Decided by: simplicity/LOC. All three publish in one shot on a 16-file tree, so the ranked performance
criterion is a tie at sub-second; the history-preserving option is eliminated outright by locked
decision D-00, and the no-wrapper option is eliminated by ROADMAP success criterion 3 — leaving the
wrap-then-copy-and-init path as both the mandated and the shortest correct one.
