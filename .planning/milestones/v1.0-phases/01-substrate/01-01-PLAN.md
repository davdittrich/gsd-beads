<verified_environment_facts>
These were confirmed by running the real `bd` v1.2.1 binary during planning. They correct three
places where 01-RESEARCH.md's Code Examples would fail against a real database.

1. **`bd` derives its issue-id prefix from the database, not a fixed `bd-`.** In a repo named
   `bdtest`, `bd create --id bd-gsdp01` fails with `prefix mismatch: database uses 'bdtest-'`.
   RESEARCH.md's `bd create --id 'bd-42'` and `<beads-id>bd-a1b2c3</beads-id>` examples are
   therefore illustrative only. **Do not pass `--id`.** Let `bd` assign the id and capture it from
   the command output.
2. **Child ids are hierarchical.** `bd create --parent <epic>` yields `<epic-id>.1`, `<epic-id>.2`.
   Ids are assigned sequentially, so a second create for the same task produces a *new* id — which
   is exactly why resolve-by-`<beads-id>`-before-create is mandatory, not merely tidy.
3. **`bd create --id` on an existing id exits 1** with `already exists; use bd update, or bd import
   for upsert semantics`. Explicit-id create is not an idempotency mechanism.
4. **`bd list --parent <epic> --json` returns only the children, not the epic** (2 children →
   2 records). B1's acceptance criterion holds as written against the `--json` form. The
   human-readable `bd list --parent` view counts differently; always use `--json`.
5. **`bd list --parent` omits closed issues by default.** Any idempotency or divergence check that
   must see closed issues needs an explicit status filter.
</verified_environment_facts>

<design_decisions>
Two decisions this plan locks, both flagged in 01-RESEARCH.md as left to the planner.

**Epic id persistence.** The epic id is written to the PLAN.md frontmatter as a top-level
`beads_epic:` key on first sync. It is NOT derived by string-splitting a task's `<beads-id>`, and
it is NOT stored in `BEADS.md` (which Phase 2/B11 defines as regenerated every step and therefore
unable to hold authoritative state). Explicit and greppable, consistent with D-03's rule that
identity is recorded, never inferred.

**Fail-open detection point (B6/D-08).** `bd` usability is checked once, at the top of
`sync.py`, by locating the binary and running one cheap read command. Absent, non-zero exit, or
timeout all take the same path: print the notice, append to STATE.md, exit 0.

**No `checkpoint:decision` precedes the one-way task, deliberately.** `verify plan-structure`
warns that Task 1 carries a `one-way` rating with no preceding decision checkpoint. That warning
is accepted here: `gsd-core/references/planner-reversibility.md` lists "gating a decision already
made" as an anti-pattern — "if the phase CONTEXT.md records the human choosing this exact option,
the door is already walked through. Keep the rating for the record; do not insert a checkpoint to
re-ask." D-01 was chosen by the developer during `/gsd-discuss-phase` on 2026-08-15, and
PROJECT.md's Key Decisions table and Binding Model were already rewritten to match. The rating is
kept so the signal survives; the checkpoint is omitted so the developer is not asked to re-decide
a decision they already recorded.
</design_decisions>
