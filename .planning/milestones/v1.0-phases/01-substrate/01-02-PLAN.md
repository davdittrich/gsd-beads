<dependency_derivation_decision>
01-RESEARCH.md Open Question 3 is left explicitly to the planner. This plan resolves it.

D-04 says only explicit "depends on" edges become `bd dep add` calls, and wave grouping is never
an implicit dependency. 01-RESEARCH.md verified there is no per-task `depends_on` field in the
real schema, so "explicit edge" resolves to exactly two sources and no third:

1. **Intra-plan order.** Within one plan, task *k* is blocked by task *k-1*, derived from position
   in the `<tasks>` array. This is a real declared ordering, not wave grouping: gsd-core's
   executor enforces a hard gate that blocks task *k* until task *k-1*'s acceptance criteria pass.
   B2's own acceptance criterion ("task 3 depending on task 1 shows task 1 as a blocker") requires
   these edges to exist at all.
2. **Inter-plan order.** The plan-level `depends_on` frontmatter array. The dependent plan's
   **first** task is blocked by the **last** task of each named prerequisite plan —
   first-blocks-on-last. `bd ready`'s blocker awareness is transitive, so chaining through the
   intra-plan edges gates the whole downstream plan with the fewest edges written.

**Explicitly not an edge source:** the `wave` frontmatter number. A plan in wave 2 whose
`depends_on` is empty gets no edge to anything in wave 1. This is D-04's rule applied literally
and is asserted by a dedicated test case, because it is the one place where an over-eager
implementation would silently violate a locked decision.
</dependency_derivation_decision>
