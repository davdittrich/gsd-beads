<scope_matching_fact>
02-RESEARCH.md verified `bd` v1.2.1 carries no structured "linked files" field, and Phase 1's own
`resolve_issue` creates every task issue with a title only (no `--description`/`--metadata`). D-01's
"file-path overlap" therefore resolves to two distinct, non-overlapping techniques that
`beads-recall` must implement, not one generic comparison:

1. **Reverse lookup via `<beads-id>` (covers this project's own issues).** For each open issue,
   scan every `PLAN.md` across every phase directory (`.planning/phases/*/*-PLAN.md`) for a task
   whose `<beads-id>` matches. That task's `<files>` element is the file-scope signal; compare
   those paths against the phase being planned.
2. **`bd list --desc-contains <fragment>` (covers issues this project's sync never created).** For
   an open issue with no matching `<beads-id>` anywhere, the only file-path signal `bd` can supply
   is a substring match against the issue's free-text description/notes.

Since no `PLAN.md` exists yet for the phase being planned at `plan:pre` time, "the phase's expected
scope" is read from the phase's own `ROADMAP.md` section text plus `CONTEXT.md`'s domain-boundary
prose (D-01, revised) — a weaker signal than a real `files_modified` list, but the only one
available pre-plan.

An issue matching neither technique, and not parented under a prior phase's epic that shares files
nor carrying a label naming the capability area, is never silently dropped (D-02) — it is listed
under a separate "Unscoped" heading so the planner can judge relevance without a false claim that
it definitely touches this phase.
</scope_matching_fact>
