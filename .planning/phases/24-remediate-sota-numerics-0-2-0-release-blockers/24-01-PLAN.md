## Alternatives Considered

- **Regex line-scan masking inside the existing pre-pass**: extend `mask_fenced_regions`, the function that already blanks fenced spans, to also blank indented code blocks and leading YAML frontmatter. Stdlib `re` only, no dependency, and the CommonMark rules for both constructs are line-oriented, which is what a line scan reads natively (`https://spec.commonmark.org/0.31.2/#indented-code-blocks`, 2024). Roughly 25 added lines in a function the suite already covers.
- **A real CommonMark parser**: replace the hand-written scan with `markdown-it-py`, which is CommonMark-compliant and exposes a token stream where code blocks and inline content are already separated (`https://markdown-it-py.readthedocs.io/en/latest/`, 2025). Correct by construction for every masking case this gate will ever meet, but it adds a runtime dependency to a capability whose install path is a plain file copy with no package step, and the gate runs inside a lifecycle hook where an import error becomes a halt.
- **A hand-rolled block-structure scanner**: parse the document into CommonMark block nodes before any regex runs, rather than masking spans in place. The GSD capability guidance ranks deletion and reuse above new structure (`.gsd/capabilities/sota-numerics/fragments/planner-sota.md`, 2026), and this option adds the most new code of the three while reproducing what option two already ships.

Decided by: simplicity. Option one adds about 25 lines to an existing function with an existing test class; option two is more correct in the abstract but trades a dependency-free single-file capability for correctness the corpus does not exercise; option three writes the most code for the least gain. Performance does not separate them at corpus scale, so the next-ranked criterion decides.
