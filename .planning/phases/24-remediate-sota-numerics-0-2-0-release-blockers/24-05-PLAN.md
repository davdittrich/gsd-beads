<objective>
Stop the shipped bundle from resolving an executable path out of the caller's working directory.

`hooks/gsd-tools.sh` locates the node entry point from the repository enclosing the invoking working directory, so a hostile repository in that position gets code execution on a `SessionStart` or `SubagentStart` hook. It is byte-identical to `origin/main`, which makes it pre-existing rather than introduced here, and it ships with 0.2.0, which is why it is fixed here (D-13). The gate command in `capability.json` carries the identical pattern in the same shipped bundle on the same lifecycle, so it is in scope too (D-14).

Purpose: this is the only finding in the phase that is exploitable by a third party rather than merely wrong. Output: two resolution paths that no longer widen to an enclosing repository, a regression test that proves it, and documentation that matches.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| invoking working directory to hook execution | A `SessionStart` or `SubagentStart` hook runs with whatever working directory the session was opened in, which the session owner does not control if the directory came from a clone. |
| enclosing repository to gate execution | The gate command runs through `sh -c` and previously derived a script path from the repository enclosing the working directory. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-24-17 | Elevation of Privilege | `hooks/gsd-tools.sh` provider resolution | critical | mitigate | A hostile repository in the working directory supplies the node entry point every hook then runs; Task 1 anchors resolution to the sourced file's own location and deletes the working-directory rung. |
| T-24-18 | Elevation of Privilege | gate predicate command in `capability.json` | high | mitigate | The same pattern resolves a Python script from the enclosing repository; Task 2 deletes that rung and pins it with a hostile-working-directory test case. |
| T-24-19 | Tampering | fail-closed guard in the gate command | high | mitigate | Removing a rung must not soften the guard that stops an uninstalled capability from silently passing every plan; a check asserts the guard message survives verbatim. |
| T-24-20 | Spoofing | documentation describing the old order | medium | mitigate | README and NOTES stating a resolution order the code no longer performs would mislead an operator auditing the fix; Task 3 corrects both and a check asserts no document names the removed lookup. |
| T-24-21 | Denial of Service | provider unresolvable after the change | medium | mitigate | Both shell suites that source the file are run, and the exit status of 127 for an unresolvable provider is asserted unchanged, so the fix cannot silently disable the hook path. |
</threat_model>

## Alternatives Considered

- **Anchor to the sourced file's own location**: derive the plugin root from the path bash reports for the file currently being sourced, preferring a host-set plugin-root variable when present. This is the anchor `session-start.sh` already uses at its line 4, so the fix goes with the grain of the bundle rather than introducing a second convention, and the bash variable that reports the sourcing file is the documented way to do it (`https://www.gnu.org/software/bash/manual/bash.html#Bash-Variables`, 2024). Roughly four changed lines.
- **Anchor to the host-provided plugin root alone**: use only the plugin-root variable the host sets for a loaded plugin, with no fallback. Simplest possible change, and it is what the plugin host documents for locating plugin files (`https://docs.claude.com/en/docs/claude-code/plugins`, 2025). It fails when the hook is run outside the host that sets it, which the capability's own notes call out as the reason that variable is not relied on at any rung today.
- **Keep the working-directory rung and harden it**: pass the repository directory explicitly to Git and refuse a result outside an allowlist, rather than removing the rung. Git's own guidance for this class of problem is the ownership check it added for exactly this attack shape (`https://git-scm.com/docs/git-config#Documentation/git-config.txt-safedirectory`, 2025). It keeps a working-directory-derived path in the resolution at all, which is the property D-13 removes, and it is the largest of the three changes.

Decided by: simplicity. Option one is the smallest change that removes the property rather than fencing it, and it reuses an anchor the bundle already computes; option two loses the non-host invocation the capability deliberately supports; option three keeps the dangerous input and adds a filter, which is more code guarding a path that has no reason to exist. Performance does not separate them.

### Internal design alternatives

- **Delete the gate command's middle rung versus anchoring it**: a command string executed through `sh -c` has no path of its own to anchor to, so deletion is the only instance of "not the caller's working directory" available there; the first rung already reaches the project copy, which is where gsd-core dispatches the gate from.
- **One fix in the sourced file versus one in each sourcing hook**: both hooks source the same file after computing their own plugin root, so a single fix in the sourced file covers both and cannot drift between them.
