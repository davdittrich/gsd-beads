**Areas discussed:** Grant visibility, Re-grant detection cadence, Auto-grant failure handling, Shared mechanism shape

---

## Grant visibility

| Option | Description | Selected |
|--------|-------------|----------|
| Silent always | No output ever; matches beads' fail-open philosophy but bypasses CB-3 with zero trace | |
| Notice on grant/re-grant | One line printed every time a grant or re-grant fires; nothing when already valid | ✓ |
| Notice on change only | Same but suppressed if bundle content matches last-granted state | |

**User's choice:** Notice on grant/re-grant
**Notes:** None.

---

## Re-grant detection cadence

| Option | Description | Selected |
|--------|-------------|----------|
| Every SessionStart | Deterministic, no degraded window, alongside existing bd prime hook | ✓ |
| Lazy, at first use | Cheaper but leaves a window where a phase could dispatch to a degraded capability | |

**User's choice:** Every SessionStart

Follow-up (hash scope):

| Option | Description | Selected |
|--------|-------------|----------|
| Whole bundle dir | Hashes every file under .gsd/capabilities/<id>/ — matches gsd-core's own consent hash and the documented invalidation trigger | ✓ |
| capability.json only | Cheaper but misses fragment/skill edits that gsd-core's own consent check still invalidates on | |

**User's choice:** Whole bundle dir

Follow-up (timing):

| Option | Description | Selected |
|--------|-------------|----------|
| Synchronous, before continuing | Blocks session start until install completes; matches bd prime's existing pattern | ✓ |
| Fire-and-forget | Faster perceived startup, but risks racing the first lifecycle dispatch after a fresh checkout | |

**User's choice:** Synchronous, before continuing
**Notes:** None.

---

## Auto-grant failure handling

| Option | Description | Selected |
|--------|-------------|----------|
| Visible warning | Print one line, then fail open; capability stays inactive, phase continues | ✓ |
| Silent fail-open | Matches bd's existing convention exactly, but harder to debug why a capability never activates | |

**User's choice:** Visible warning
**Notes:** Deliberately diverges from beads' existing silent-fail-open convention because this path is now unattended.

---

## Shared mechanism shape

| Option | Description | Selected |
|--------|-------------|----------|
| One shared script | Single file both plugins' hooks.json invoke directly | (initially selected, then reconsidered) |
| Per-plugin copy | Each plugin embeds the same logic independently | |

**User's choice (initial):** "1, but what happens if only one of the three plugins is installed by the user? They are separate products."

**Notes:** User flagged that a true shared runtime file breaks for a user who installs only one of the three separately-installable marketplace plugins. Follow-up question posed to resolve the constraint:

| Option | Description | Selected |
|--------|-------------|----------|
| Vendored copies, one source | Identical script authored once, copied into each plugin's own hooks/ dir at packaging time — no runtime cross-plugin dependency, each plugin stays standalone-installable | ✓ |
| Tiny shared dependency plugin | A 4th minimal plugin ships the script; others declare it as a required marketplace dependency — introduces a new install-order failure mode | |

**User's final choice:** Vendored copies, one source
