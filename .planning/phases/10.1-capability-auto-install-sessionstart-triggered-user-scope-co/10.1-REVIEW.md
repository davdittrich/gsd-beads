# Phase 10.1: Code Review Report

**Reviewed:** 2026-08-17T00:00:00Z
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

Reviewed the SessionStart-triggered, user-scope capability auto-install mechanism and its
`ponytail-everywhere` consumer (hooks, vendored-copy CI parity gate, capability bundle,
smoke tests, and release packaging). The core `capability-auto-install.sh` script itself is
careful and well-defended (CAP_ID regex validation before any path construction, portable
hash-tool selection, non-silent failure paths per D-04, correct `$?` propagation through the
`gsd_tools` shim, and a byte-identical vendored twin verified independently against the
shipped copy). The two vendored copies (`hooks/` and `ponytail-everywhere/hooks/`) and the
two `.gsd/capabilities/ponytail` bundle copies are confirmed byte-for-byte identical
(re-verified with `diff`/`diff -r`, not just trusted from the CI step definition).

The most consequential issue is in `release.yml`: the commit that added `.gsd` to the
release-zip allowlist states its purpose is to "ship capability bundles like the
marketplace clone does," but the zip never includes `ponytail-everywhere/` at all — so the
GitHub Release archive cannot deliver the second plugin `marketplace.json` advertises. The
remaining findings are a silent symlink gap in the bundle-hash drift detector, a test-isolation
gap in the auto-install smoke test, and a content inconsistency between the two "ponytail
lite" advisory-text definitions.

## Critical Issues

### CR-01: Release zip cannot deliver the `ponytail-everywhere` plugin

**File:** `.github/workflows/release.yml:16-24`
**Issue:** `marketplace.json` declares two plugins sourced from this repo: `beads-lifecycle`
(`./`) and `ponytail-everywhere` (`./ponytail-everywhere`). The release workflow's zip
allowlist is:
```yaml
zip -r gsd-beads.zip \
  .claude-plugin \
  hooks \
  .agents/skills \
  .gsd \
  README.md \
  LICENSE
```
This bundles only the root plugin's own `.claude-plugin/plugin.json`, `hooks/`, and skills.
`ponytail-everywhere/.claude-plugin/plugin.json`, `ponytail-everywhere/hooks/` (which contains
the `SubagentStart`-wired `session-start.sh`, `capability-auto-install.sh`, `gsd-tools.sh`,
and `hooks.json` that actually deliver the ponytail advisory banners), and
`ponytail-everywhere/tests/` are entirely absent from the archive. The root `.gsd/`
directory that *is* zipped happens to contain a redundant copy of the `ponytail` capability
bundle (`.gsd/capabilities/ponytail/`, used for this repo's own dogfooding per
`NOTES.md`'s "Toggle-testing gotcha" section) but that copy carries no plugin manifest and no
hook wiring on its own — it cannot register or run `ponytail-everywhere` as an installable
plugin.

The commit that introduced this line (`445deb0`, message: "release.yml: add .gsd to the zip
allowlist so the release artifact ships capability bundles like the marketplace clone
does") explicitly states the goal of matching the marketplace-clone install path. It only
achieves that for the root plugin; anyone installing from the GitHub Release archive rather
than `claude plugin marketplace add` gets a broken/missing second plugin with no error
surfaced anywhere in the workflow.

**Fix:**
```yaml
zip -r gsd-beads.zip \
  .claude-plugin \
  hooks \
  .agents/skills \
  .gsd \
  ponytail-everywhere/.claude-plugin \
  ponytail-everywhere/hooks \
  ponytail-everywhere/.gsd \
  README.md \
  LICENSE
```
(or split into two archives / two release assets, one per plugin, if a single combined zip is
not the intended distribution shape for a two-plugin marketplace).

## Warnings

### WR-01: `bundle_hash` silently excludes symlinks, defeating drift detection for them

**File:** `hooks/capability-auto-install.sh:36-40` (byte-identical in
`ponytail-everywhere/hooks/capability-auto-install.sh:36-40`)
**Issue:**
```bash
bundle_hash() {
  {
    find "$BUNDLE_DIR" \( -type f -o -type d \) | LC_ALL=C sort
    find "$BUNDLE_DIR" -type f | LC_ALL=C sort | while IFS= read -r _f; do cat "$_f"; done
  } | "${HASH_CMD[@]}" | awk '{print $1}'
}
```
`find`'s `-type` test uses `lstat` by default (no `-L`/`-follow`), so a symlink's type is `l`,
matching neither `-type f` nor `-type d`. Any symlink anywhere under `$BUNDLE_DIR` — a
symlinked fragment file, a symlinked subdirectory — is invisible to both the path-listing
component and the content-concatenation component of the hash. The comment directly above
this function claims "every path under the bundle (files AND directories...)" is covered;
symlinks are a silent gap in that guarantee. Editing what a bundle symlink points at, or
adding/removing one, would never trigger re-install (D-02/D-03 drift detection defeated for
that content). No bundle in this repo currently contains a symlink, so the gap is latent, not
yet triggered.
**Fix:** Add `-o -type l` to the first `find`, and either dereference-and-hash symlink targets
explicitly or hash the `readlink` target path (to detect a re-pointed symlink even when the
target's own bytes are unchanged):
```bash
find "$BUNDLE_DIR" \( -type f -o -type d -o -type l \) | LC_ALL=C sort
```

### WR-02: Auto-install smoke test isn't structurally isolated from the ambient git repo

**File:** `tests/test-capability-auto-install.sh:55-59, 62, 80, 89, 170-176`
**Issue:** `run_script()` invokes `bash "$SCRIPT" "$1"` without changing directory, so cases
1-4 and case 6's "CLAUDE_PLUGIN_ROOT-set" run execute with cwd still inside this real git
repository. `gsd_tools()`'s first resolution branch (inlined in the script under test) runs
`git rev-parse --show-toplevel` and, if that succeeds, prefers
`$_root/gsd-core/bin/gsd-tools.cjs` over the PATH-stubbed `gsd-tools` used everywhere else in
the suite. Today this repo has no `gsd-core/bin/gsd-tools.cjs`, so the stub still wins and the
assertions hold — but that's an incidental fact about the repo's current contents, not
something the test enforces. The suite's own author was clearly aware of this exact hazard:
case 5 (lines 111-139) deliberately `cd`s into a non-repo `WORKDIR` and restricts
`PATH="/usr/bin:/bin"` specifically to neutralize this branch and force the 127 path. The same
neutralization is not applied to cases 1-4 or case 6, so those cases would silently start
exercising a different code path (and stop testing the PATH-stub contract they assert on) the
moment a `gsd-core/bin/gsd-tools.cjs` is vendored into this repo.
**Fix:** Run cases 1-4 and case 6 from a non-repo scratch cwd the way case 5 already does
(e.g., add `cd "$SCRATCH"` — or a dedicated non-git subdirectory of it — inside `run_script`),
or `git -C` neutralize by unsetting/overriding what `git rev-parse` resolves to for the
duration of the test.

### WR-03: The two "ponytail lite" advisory texts disagree on what lite covers

**File:** `ponytail-everywhere/hooks/session-start.sh:61` vs.
`ponytail-everywhere/.gsd/capabilities/ponytail/fragments/executor-ladder.md:3`,
`fragments/planner-ladder.md:3`, `fragments/verifier-ladder.md:3`
**Issue:** The capability-contribution fragments (injected via `plan:pre`, and declared
forward-compatible no-ops at `execute:wave:pre`/`execute:wave:post`) all state:
> "lite applies rungs 1-2 only (does this need to exist at all, is it already in this
> codebase)"

But the `SubagentStart`-triggered banner in `session-start.sh`, which is the mechanism
`NOTES.md` itself identifies as the *actual* execute/verify-time reach today, defines lite
differently:
```bash
lite) BODY='YAGNI first, then reuse what is already here, then stdlib, then the shortest working diff.' ;;
```
This covers rungs 1, 2, 3, and 7 (or 6) — materially more than "rungs 1-2 only." An agent
that receives the fragment text (planning) is told lite stops at rung 2; an agent that
receives the `SubagentStart` banner (execution) is told lite also includes stdlib-first and
shortest-diff. Same advisory concept, same `ponytail.level=lite` value, two different
definitions depending on which delivery path fired.
**Fix:** Make `session-start.sh`'s `lite` `BODY` match the fragments' "rungs 1-2 only"
definition (or vice versa — update the fragments if the broader lite definition is the
intended one), so `ponytail.level` means the same thing regardless of which hook delivered it:
```bash
lite) BODY='Rungs 1-2 only: does this need to exist at all (YAGNI), is it already in this codebase (reuse it).' ;;
```
