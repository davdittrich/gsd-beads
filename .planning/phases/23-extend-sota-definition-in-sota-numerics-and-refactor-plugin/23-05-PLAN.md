## Alternatives Considered

- **Merge to `main` as the publish, with review and its accepted fixes landed on the branch first, CI verified on the exact merged commit, then an annotated `v0.2.0` tag**: no cross-repository change, and the tag records what was served without becoming the mechanism that serves it. Citation: the marketplace entry `` `/home/dd/projects/gsd-beads/.claude-plugin/marketplace.json` `` — `source.url` is `https://github.com/davdittrich/sota-numerics.git` with no `ref` key, read directly and verified 2026-09-06; and `` `.github/workflows/ci.yml` `` triggers on both `push` and `pull_request`, verified 2026-09-06, so the branch carries green signal before any pull request exists.
- **Tag-gated release: pin the marketplace entry to a `v0.2.0` ref and publish by moving that pin**: makes releases immutable and separates merging from publishing, which is the shape [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html) presumes when it treats a version as a fixed artifact (spec published 2013, re-read 2026-09-06). Rejected on scope and coordination: the entry lives in a second repository whose editing this phase's locked decisions place out of scope, and adopting it would leave two repositories that must move together on every future release with nothing enforcing that they do. The convention itself is genuinely unsettled and is tracked as bd issue gsd-beads-oh1 rather than dropped.
- **Open the pull request first and let external review drive the fixes**: the conventional flow, where the pull request is both the review venue and the CI trigger. Rejected because the merge is the publish here: a fix accepted after the pull request opens means the artifact a reviewer approved is not the artifact installers receive, and a reviewer's first pass on a known-incomplete diff is a wasted pass rather than a safety net. CI is not a reason to open early — `` `.github/workflows/ci.yml` `` already runs on `push`, verified 2026-09-06, so the branch has full signal with no pull request at all.

Decided by: simplicity. Performance does not separate these — none of the three has a runtime cost — so the decision falls to the next ranked criterion, and the chosen path is the only one requiring zero changes outside this repository and zero standing coordination between two repositories on every future release. It reaches the same immutability the tag-pinned option offers, through a tag that records rather than gates, at a fraction of the moving parts.

### Internal design alternatives

- **Verifying CI on the merged commit versus on the pull request head**: on the merged commit. A squash or merge commit produces a SHA the pull request never ran against, and that SHA is what every installer receives. Task 3 re-queries check-runs against `origin/main` after the merge for exactly this reason.
- **Tagging before the merge versus after CI confirms green**: after. A tag created early would name a commit that had not yet been proven, and correcting it means deleting a ref other people may already hold.
- **Blocking watchers versus polling loops for CI**: `gh pr checks --watch` and `gh run watch` block until the run finishes and exit on its conclusion; a polling loop burns turns and can miss a transition.
