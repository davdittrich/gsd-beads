## Alternatives Considered

- **Extend the existing five `## What it changes` rows**: document each added dimension inside the row for the lifecycle point whose fragment carries it, so a fragment and its documentation stay in the same row of the same table. Citation: `` `README.md` `` lines 9-15 and the four-entry `contributions` array in `` `.gsd/capabilities/sota-numerics/capability.json` ``, both read directly and verified 2026-09-06. The table already has exactly one row per contribution point plus one for the gate, so the mapping is already established and needs no new structure.
- **Add a new section listing the six dimensions**: give the extended definition its own level-two section with one entry per dimension. Rejected because it creates a second place the definition lives, so a later fragment edit silently desynchronizes the README — the same duplication this repository is already paying down elsewhere, since `` `.gsd/capabilities/sota-numerics/NOTES.md` `` is being pruned in this very plan precisely on the grounds that README states part of it (read and verified 2026-09-06). Cost is real too: [Anthropic, "Effective context engineering for AI agents" (2025)](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) and [Chroma Research, "Context Rot" (2025)](https://www.morphllm.com/context-rot) both make the case that added length degrades comprehension monotonically, and a section restating four fragments is pure addition.
- **Point README at the fragment files instead of describing them**: replace the Behavior cells with references to `fragments/*.md`. Rejected on reachability. The marketplace entry serves this repository by URL with no ref — `source.url` is `https://github.com/davdittrich/sota-numerics.git` in `` `.claude-plugin/marketplace.json` `` (verified 2026-09-06) — so README is frequently read as a rendered listing page where the four fragment files are not one click away, and a reader deciding whether to install would have to open four files to learn what the plugin does.

Decided by: maintenance. Performance is a wash across all three: README is not injected into any prompt, so its length costs a human reader's attention rather than an agent's context budget, and the criterion that normally decides this class of question does not separate the options. Simplicity and LOC slightly favor the pointer option, which is the shortest, but it fails on reachability rather than on cost. What separates the three is which one stays true without anyone remembering to update it, and only the table row does: the row and its fragment are the two halves of one claim, sitting in one place, with the claim-trace command holding them honest.

### Internal design alternatives

- **Line-by-line prune of NOTES.md versus deleting whole sections**: line by line. Three of the five sections have a README-covered half and an uncovered half; deleting either whole section would lose an anti-regression entry, and keeping either whole section would leave the duplication the decision asks to remove.
- **Auditing README claims before editing versus after**: before. Running the claim-trace command first distinguishes a claim that Plans 01 through 03 invalidated from a claim that was never backed, and the twelve-claim baseline was proven green on the unmodified tree so a red line is signal rather than noise.
- **Recording the claim-to-source map in the summary versus in a repository file**: the summary. A file in the repository would be new documentation infrastructure for prose, which is exactly what the decision forbids, and it would immediately become a third place the same facts live.
