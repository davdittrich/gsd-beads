## D-04: what happens to a project that already wrote a value into `.planning/config.json`

CONTEXT.md leaves the shape to Claude's discretion but requires it be stated explicitly, cover
both cases, and not invent a reader purely to deprecate. Stated:

**Case 1 — a project already holding the mirror value.** No notice, no migration, no code path.
The value was inert; it becomes meaningful. The behavior such a project sees on upgrade is that
an explicit `sync.py create-issues` stops stripping task bodies — which is precisely what someone
who wrote that value was asking for. It is nonetheless **a live behavior change on upgrade, not a
no-op**, so `CHANGELOG.md` records it under `### Changed`, naming the projects affected and what
changes for them. Recording it as a fix would understate it.

**Case 2 — a project already holding the retired value, or any other value outside the declared
list.** One line at `plan:pre`, printed to stdout so the plugin hook promotes it into
`additionalContext`. It fires once per `plan:pre` dispatch, names the offending value verbatim,
states that the shipped default applies, and gives the one-command remedy. It is a notice, never
an error.

**Why a notice at all.** Research established there is genuinely no passive detection channel in
gsd-core: the unknown-key warning enumerates only top-level keys and never descends into a
namespace, `validate health` has no capability-config rule at all, and `config-get` returns a
stale value verbatim with exit 0 and empty stderr. So with the value merely retired, an actual run
produces **no observable output whatsoever** — indistinguishable from a broken notice, which is
exactly what ROADMAP Success Criterion 3 forbids. `config-set`'s validator does not qualify: it
fires only when a user re-writes a key they will never re-write.

**Why `plan:pre` and not somewhere else.** `lifecycle_dispatch` already runs unconditionally at
that point, in the same function that already prints two patch-loss diagnostics through the same
channel. No new dispatch, no new hook, no new point — one more line in a place a user already
reads once per phase plan.

**Why a notice rather than a hard error.** Every lifecycle hook is `onError: skip` and
`lifecycle_dispatch` always returns 0; nothing this phase adds may break that. gsd-core's own
config-removal precedent (`runtime.hostBehaviors.reviewerCli`) also warned and never errored.

**What is deliberately NOT done.** The capability does not write, rewrite, or delete anything in
`.planning/config.json`. No auto-migration. Reading a user's config and silently editing it is a
materially larger permission than making a declaration true, and this milestone is about the
latter. This is recorded as a prohibition in `must_haves`, not merely as prose.
</migration_answer>

## Alternatives Considered

The roadmap left this direction open and required a table covering three options. A fourth was
supplied during discussion and is the one implemented. **The three research documents disagree
with each other and the disagreement is resolved below, not averaged.**

- **(a) Narrow the declaration and docs to what the code does** — keep the key, delete the two
  unimplemented values, change nothing behavioral. Sources: `` `.planning/research/ARCHITECTURE.md` ``
  and `` `.planning/research/PITFALLS.md` `` §C1 (both 2026-08-19) recommend this, C1 specifically
  because dropping the key produces zero observable output for an existing user; the sibling
  `` `~/.gsd/capabilities/sota-numerics/capability.json` `` states the "declare one key, mean it"
  stance outright (read 2026-08-20). **Decided by:** rejected on **simplicity/LOC** — not because
  it is complex, but because it is *strictly worse than (d) at equal cost*. Both edit the same
  declaration; (d) additionally makes one of the deleted values real for the price of a two-line
  accessor over a helper that already exists. Deleting a value whose behavior the code already
  implements privately is throwing away work.

- **(b) Implement both unimplemented values** — wire the full three-value enum. Sources:
  `` `.planning/research/FEATURES.md` `` (2026-08-19) establishes the self-read precedent, and
  `` `plugins/beads-lifecycle/.gsd/capabilities/beads/scripts/sync.py` `` lines 669-676 show the
  identical two-line accessor shape already serving two other keys (0.3.1, 2026). **Decided by:**
  rejected on **maintenance overhead** — the third value would duplicate `beads.enabled: false`,
  which is already implemented and already gates all six lifecycle steps. Two spellings of one
  behavior is a permanent support cost and a permanent question ("which one wins?") for no gain.

- **(c) Drop the key entirely** — remove the declaration and every mention. Sources:
  `` `.planning/research/FEATURES.md` `` (2026-08-19) recommends this and records zero orphan
  config keys across all four sibling plugins; gsd-core's own removal precedent is
  `runtime.hostBehaviors.reviewerCli` — <https://github.com/open-gsd/gsd-core/issues/2801> —
  one release as a derived alias, then deletion, warning never error. **Decided by:** rejected on
  **ecosystem support** — verified live on 2026-08-20, `gsd-tools config-set beads.sync_mode
  bogus` today returns `Error: Invalid beads.sync_mode 'bogus'. Valid values: ...` and refuses the
  write. Dropping the key replaces that typed rejection with a generic unknown-key error whose
  ~2000-character valid-key dump contains no `beads.*` entry at all, which a user reads as "beads
  config does not exist". Dropping removes the only error surface the key has.

- **(d) Implement the mirror value, retire the third (CHOSEN, CONTEXT.md D-01/D-02, 2026-08-20).**
  A hybrid of (a) and (b): the key stays, gains a second value that genuinely does something, and
  sheds the value that never had independent meaning. Source: the `allow_strip` parameter shipped
  in 0.3.1, documented in `` `CHANGELOG.md` `` §0.3.1 (2026-08-19), is exactly this behavior —
  implementation is wiring a config read to a flag that already exists. **Decided by:**
  **simplicity/LOC** — it is (a)'s edit plus a two-line accessor, and it is the only option that
  makes `capability.json`'s own description string true rather than aspirational: "bd owns task
  status and task content after first sync" is precisely what the mirror value does *not* do.

**How the disagreement resolves.** ARCHITECTURE and PITFALLS argue *against dropping* (keep a live
guard, keep the key discoverable); FEATURES argues *against keeping a dead declaration* (zero
orphan keys anywhere in the corpus). (d) satisfies both objections simultaneously — nothing stays
dead, and nothing gets dropped — which is why the disagreement does not need averaging. The losing
evidence loses on a specific point: FEATURES' orphan-key precedent is an argument against *dead*
declarations, and after (d) there is no dead declaration left to object to.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `.planning/config.json` -> strip decision | A user-editable value decides whether irreversible PLAN.md prose deletion is permitted on the explicit path |
