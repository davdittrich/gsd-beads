For this plan the relevant question is narrower: **the phase number stops being an integer.**

- **Primary noun:** the *phase number as an opaque string token* (previously: an integer that
  happened to be spelled as a string).
- **Decision:** `promote`. The string is promoted to the primary representation everywhere on this
  path; the integer interpretation is demoted to what it always actually was — a leading-zero
  strip. No numeric type is introduced alongside the string (D-07 forbids it), so there is no
  add-alongside asymmetry to accumulate.
- **Rationale:** the value's only consumer is regex construction. A numeric type would buy nothing
  and would reintroduce both a parse that can raise and a formatting risk (`1.50`, `1.5000000001`).
- **Invariant test (accepted, Task 2):** every phase-number form this repo has ever produced —
  `01`, `07`, `17`, `10.1`, `11.1`, `01.5` — round-trips through `phase_regex_token` and
  `phase_dir_prefix` and resolves its own ROADMAP header, so a future phase reintroducing a
  numeric conversion goes red immediately.
</assumption_delta_decision>

## Alternatives Considered

Mechanism choice: how to make a decimal phase number usable in the three regexes and the one
directory-prefix comparison that currently break.

- **String leading-zero strip + `re.escape` (CHOSEN).** The value is only ever interpolated into a
  regex, so it never needs to be a number. `re.escape("1.5")` yields `1\.5`, keeping the literal
  dot literal; the existing `0*` prefix in the header pattern keeps `### Phase 01.5:` matching.
  The sibling `sota-numerics` capability shipped the equivalent widening for its own copy of this
  regex with a comment naming beads' pattern as the too-narrow one
  (`~/.gsd/capabilities/sota-numerics/scripts/check-alternatives.py:34-37`, read 2026-08-20;
  ReDoS discipline documented in the same file). Python's `re.escape` semantics confirmed against
  the current stdlib docs — <https://docs.python.org/3/library/re.html#re.escape> (Python 3.13,
  2026). **Decided by:** simplicity/LOC — two helper functions of two lines each, no parse that
  can raise, no formatting surface.

- **`decimal.Decimal` parsing.** Exact base-10 arithmetic with no binary rounding error, which is
  the standard answer whenever a decimal literal must survive a round trip
  (<https://docs.python.org/3/library/decimal.html>, Python 3.13, 2026). Rejected: it is the right
  tool for arithmetic and this path performs none. It also *loses* information the string carries
  — `Decimal("10.10") == Decimal("10.1")` is `True`, which would silently merge two distinct phase
  directories — and reintroduces an `InvalidOperation` raise on malformed input. **Decided by:**
  performance is a tie, so simplicity/LOC decides, and Decimal costs a parse plus a formatting
  step to get back to the string the regex actually needs.

- **`packaging.version.Version` / a semver-style parser.** Purpose-built for dotted numeric
  identifiers with correct ordering and normalization
  (<https://packaging.pypa.io/en/stable/version.html>, packaging 24.x, 2026). Rejected on
  **ecosystem support**: `sync.py` is deliberately pure stdlib (RESEARCH.md "Standard Stack": no
  new external libraries this phase), and adding a runtime dependency to a capability script that
  ships inside a plugin bundle is a distribution change out of all proportion to a two-line
  leading-zero strip. Its normalization would also collapse `10.10` to `10.1`, the same
  information loss as Decimal.

Not a mechanism choice, recorded for completeness: `PLAN_FILE_RE`'s widened shape copies the
sibling capability verbatim apart from preserving beads' existing capture group.
