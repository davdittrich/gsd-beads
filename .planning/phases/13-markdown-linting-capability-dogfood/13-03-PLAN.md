## Alternatives Considered

- **rumdl `check --fix`** (selected for the D-01 cleanup): the linter's own fixer, so the fix set is
  by construction exactly the rule set the gate enforces — no second tool's opinion can leak in.
  `https://crates.io/crates/rumdl` (first published 2025-02-28; v0.2.53 confirmed live 2026-08-18);
  `rumdl check --help` confirmed live 2026-08-18 that `--fix` is a `check` option, and that a
  separate `rumdl fmt` exists with different exit-code semantics (`fmt` always exits 0).
- **`markdownlint-cli2 --fix`**: `https://github.com/DavidAnson/markdownlint-cli2`, v0.23.2 run live
  against this repo's corpus 2026-08-18. Rejected because it enforces a strictly larger violation
  set (708 vs 471 on the identical allowlist) and would therefore rewrite files the shipped gate
  never asked to change, plus it pulls in a Node>=20 dependency class for a one-off cleanup.
- **`rumdl fmt`**: same binary, but it always exits 0 and cannot signal that unfixable violations
  remain — which is precisely the signal D-01's spot-check step depends on (this session's
  measurement found 1 of 471 violations unfixable).
- **Hand-editing all violations**: rejected by D-01 explicitly; ~470 mechanical whitespace and
  heading-spacing edits by hand is strictly more error-prone than the fixer plus a diff review.

**Decided by:** simplicity/LOC (rank 2) — zero new tooling, since the fixer is the same binary the
gate already runs; performance (rank 1) is a wash for a one-off cleanup, and ecosystem support does
not discriminate here.
