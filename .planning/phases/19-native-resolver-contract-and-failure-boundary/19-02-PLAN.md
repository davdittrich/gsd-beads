## Alternatives Considered

| Mechanism | Performance | Simplicity / LOC | Ecosystem | Maintenance | Decision |
| --- | --- | --- | --- | --- | --- |
| Existing `TestResolveTaskContent._invoke` public-main seam with `mock.patch.object(sync, "run_bd", side_effect=...)` | In-process; no `bd` setup or subprocess cost | Reuses one helper and one stdlib mock per isolated arm | Existing repository pattern; Python docs specify `side_effect` raises the supplied exception | No new helper, dependency, or fixture runtime | Chosen: it exercises `main()` and resolver error mapping while isolating exactly one fault per D-18/D-19. [Python unittest.mock, 2026](https://docs.python.org/3/library/unittest.mock.html) |
| Direct `resolve_task_content()` unit calls | In-process | Slightly fewer lines | Existing function | Duplicates a lower-level seam already covered by the public contract | Rejected: misses the required public-main proof and could hide dispatch/output regressions. |
| Real unavailable `bd` executable or sleeping subprocess | Process startup and environment dependent | More fixture machinery | Python subprocess supports it | Platform and PATH sensitivity | Rejected: the already-patched typed `run_bd` seam deterministically raises `TimeoutExpired`/`OSError`; `subprocess.run()` is the standard API whose exceptions are being modeled. [Python subprocess, 2026](https://docs.python.org/3/library/subprocess.html) |

Ranked decision: performance, then simplicity/lines of code, then ecosystem support, then maintenance. Reuse the existing public seam and Python stdlib; do not add a dependency or test harness.
