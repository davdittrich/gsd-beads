<objective>
Build the sync-side half of the inversion (D-01): the detector that proves the machine-local
`execute-plan.md` patch is present, and the stripper that turns an `auto`/`tracer` task block into
a pointer once its content has actually landed in bd.

Purpose: D-01 is only real if `PLAN.md` stops carrying task instructions. Leaving both copies in
place would require PLAN.md and bd to stay in sync forever, which CONTEXT.md's D-01 names as
exactly the outcome that defeats the point. But removing content is destructive, so it is gated
twice: only for tasks whose issue was created in this same run, and only on a machine where the
executor patch that reads from bd is verifiably installed.

Output: `check_execute_plan_patch()` (clone of the proven `check_shipmd_patch` shape),
`strip_task_bodies()`, their subcommand wiring, and tests covering the checkpoint exclusion and
both gates.

Ordering note: this plan lands the stripper BEFORE plan 16-04 installs the patch. That is
deliberate and safe — with the patch absent, `strip_task_bodies` is inert, so nothing in this
phase's own in-flight plans can be reduced to a pointer mid-execution. The stripper switches on
only once 16-04 has installed the read path that can follow a pointer.
</objective>

happens: PLAN.md stops being *a* source of task content and bd becomes *the* source.

**Decision: promote, with a scoped migration boundary — not a permanent alternative path.**

- For `auto`/`tracer` tasks synced from this point on, bd is promoted to sole source. PLAN.md's

- The read path (plan 16-04) does carry a second branch for a bd issue with an empty description.
  That is NOT an alternative source living alongside the promoted one; it is the boundary marker
  for Phases 1-15's pre-inversion issues (D-07), whose PLAN.md files are never stripped and
  therefore still legitimately hold their own content. The branch is scoped to "issue exists and
  has no description", a condition that can only be true for a pre-inversion issue, and it prints

is a safety interlock, not a mode.

## Alternatives Considered

**1. Patch-loss detection: substring-check a versioned HTML marker vs. hash the installed file vs. attempt a dry-run diff apply.**
`GSD-CORE-PATCH.md` (in-repo, patch dated 2026-08-15) and `sync.py::check_shipmd_patch`
(sync.py:1553) already solve this identical problem shape for `ship.md`, and
`TestCheckShipmdPatch` already tests it. A content hash would detect any drift, not just total
loss; a dry-run diff apply would detect partial corruption. **Decided on maintenance overhead**
(rank 4): a hash breaks on every legitimate gsd-core release that touches an unrelated line of the
file, producing false alarms that train the reader to ignore the warning; the marker survives
unrelated edits and fails only when the patch is actually gone. Cloning the existing, tested shape
also means one detection idiom in this capability rather than two.

**2. Making PLAN.md a pointer: strip at sync time vs. leave PLAN.md full and let the executor prefer bd.**
Leaving PLAN.md full is zero new code and zero destructive operations. CONTEXT.md's D-01
(2026-08-19) rules it out explicitly: two copies of the same instructions require permanent
synchronization, and drift between them is silent and unresolvable at execute time. **Decided on
correctness over simplicity** — the dual-source option is smaller but does not achieve the stated
goal, which the ladder does not permit trading away.

**3. Strip scope: only tasks created in this run vs. every `auto`/`tracer` task on every sync.**
Stripping every qualifying task on every sync is a simpler predicate (one condition instead of
two) and would retroactively convert already-synced plans. **Decided on correctness/data safety**:
content may only be removed at the moment it is known to have been written, which is exactly when
`bd create` returned 0 and the id entered `task_updates`. The narrower predicate additionally
guarantees a plan already in flight — including this phase's own remaining plans — can never be
stripped out from under a running executor.

**4. Strip gate: verify the patch every run vs. a config flag vs. no gate.**
A `beads.strip_plans` config flag would be the conventional switch. `.planning/ROADMAP.md`'s
Cross-Cutting Constraints (v1.2) section states the discipline directly — "verify the patch before
trusting any gate" — and PROJECT.md records the same for the `ship.md` precedent. **Decided on
correctness**: a config flag records an intention, whereas the detector records a fact about the
machine actually executing. A flag set to true on a machine whose patch was silently stripped by a
gsd-core update would produce exactly the failure the gate exists to prevent.
