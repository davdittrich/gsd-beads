**2. Documentation home: extend the existing `GSD-CORE-PATCH.md` with a second section vs. a new `GSD-CORE-PATCH-EXECUTE.md`.**
16-RESEARCH.md's Open Question 2 (2026-08-19) frames this as a pure file-organization choice with
no functional difference and recommends extension. **Decided on simplicity** (rank 2): one
canonical answer to "what is patched on this machine" is one file to check after a gsd-core
update, and one place a reapply procedure lives. A second file adds a second thing to remember to
look at, for zero behavioral gain.

**3. bd read invocation: `bd show <id> --json` vs. `bd show <id> --json --long` vs. `bd show --id=<id>`.**
`bd show --help` on this machine (checked 2026-08-19) documents `--long` as adding extended

scratch-database check confirms `description` and `acceptance_criteria` are present in default
`--json` output whenever non-empty. `--id=<id>` exists for ids that look like flags. **Decided on
simplicity/LOC** (rank 2): the plain form returns everything needed; `--long` would be harmless
but unnecessary noise, and `--id=` matters only for id shapes bd's own prefix scheme does not
produce here.
