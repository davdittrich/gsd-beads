## Alternatives Considered

**1. Phase-wide reconciliation at `verify:post` vs. hardening the `execute:wave:post` dispatch prose vs. a git-log-based completion detector.**
16-RESEARCH.md's D-08 investigation (2026-08-19) established that `close_wave` and
`find_completed_task_ids` are correct and that completion has never been detected via git log at
all — only SUMMARY.md existence. Hardening the dispatch prose is the intuitive fix, but the same
research shows the dispatch is a natural-language instruction inside a long orchestrator workflow
and that no `*-BEADS.md` has been produced by any phase since Phase 4, so there is no way to
verify prose hardening worked. A git-log-grep completion detector would be a genuinely new
mechanism competing with the SUMMARY.md-existence one. **Decided on simplicity/LOC** (rank 2): the
reconciliation composes `_resolve_completed_task_ids` (sync.py:696) and `filter_open_ids`
(sync.py:753) — two functions that already exist and are already tested — so the only new code is
a call site and its fail-open guard, and its effect is directly assertable in a test.

**2. Closing the four stale issues: the new `reconcile-stale-closed` vs. the existing `close-wave 14-02 14-03` vs. a hand-typed `bd close`.**
16-RESEARCH.md recommends the `close-wave` route as zero-new-code remediation (sync.py:784, both
plans' SUMMARY.md files already committed). A hand-typed `bd close` would be one command.
**Decided on ecosystem support** (rank 3): running the new subcommand against real data proves the
backstop this plan just added works on production data, not only on fixtures — one action that is
both the remediation and D-08's required proof, versus two actions where the proof is weaker. The
`close-wave` route stays available and is named in the SUMMARY as the fallback if the new
subcommand misbehaves.

**3. Reason string: a distinct phase-wide reason vs. reusing `close_wave`'s `wave complete: ...` wording.**
Reusing the existing string is fewer characters. **Decided on maintenance overhead** (rank 4): the
`close_reason` field is the only durable record of which mechanism closed an issue, and a future
investigation like D-08's own would be materially harder if a backstop close were indistinguishable
from a wave close in `bd show --json`.

## Known Ceiling (16-RESEARCH.md Assumption A3)

The backstop is dispatched from `verify:post`, and `verify:post`'s own dispatch is an instruction
of exactly the kind that was empirically skipped — the same research that motivates this plan also
found that `regenerate_beads_md`, which `verify:post` already calls, has produced a `*-BEADS.md`
file exactly once in this project's history. So this plan reduces the failure probability from
once-per-wave to once-per-phase; it does not eliminate it.

That residual is accepted deliberately rather than pre-emptively engineered around. The upgrade
path, if `verify:post` is ever observed to miss a reconciliation: dispatch the same idempotent
subcommand from a second, independent lifecycle point — `beads-recall`'s `plan:pre` step is the
one dispatch point with direct evidence of firing (this phase's own `16-BEADS-RECALL.md` was
generated by it), and reconciling the *previous* phase at the next phase's `plan:pre` is the right
semantics for a backstop-of-a-backstop. Building it now would mean writing previous-phase
resolution logic against a risk that has not yet been observed for this command. The signal is
being reported upstream instead — plan 16-04 Task 3 files the dispatch-reliability finding with
its concrete evidence.
