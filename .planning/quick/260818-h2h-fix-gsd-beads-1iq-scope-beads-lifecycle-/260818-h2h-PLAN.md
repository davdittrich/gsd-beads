## Root-Cause Correction (read before executing)

The bd ticket and the planning brief both assert that gsd-core's capability loader
auto-discovers `.gsd/capabilities/<id>/` under an *installed plugin's* root, and that this
is what produces the live `sota-numerics` id collision. **That is not what the code does.**
Verified directly:

- `~/.claude/gsd-core/bin/lib/capability-loader.cjs:220-289` (`overlayRoots`) builds exactly
  two overlay roots: global `$GSD_HOME/.gsd/capabilities` and project
  `<projectRoot>/.gsd/capabilities`. There is no plugin-root scan anywhere in
  `bin/lib/*.cjs`. (Confidence: 95 — read the function body and grepped the lib dir.)
- A plugin's bundle only becomes live via the explicit
  `gsd_tools capability install "$BUNDLE_DIR" --scope global --yes` call in
  `hooks/capability-auto-install.sh`, and `hooks/session-start.sh` invokes it with the
  hardcoded literal `beads` — never `sota-numerics` or `ponytail`. (Confidence: 95.)
- The collision observed from this repo is **project-scope dogfood copy vs. global installed
  copy**: running `node ~/.claude/gsd-core/bin/gsd-tools.cjs loop render-hooks plan:post --raw`
  from the repo root emits the warning; running the identical command from a scratch project
  outside the repo emits no warning. The two `capability.json` files are byte-identical, and
  the surviving (global) registration still renders an active `sota-numerics` `plan:post`
  gate. (Confidence: 95 — both runs executed, outputs compared.)

**Consequence for this plan — REVISED.** Under the plan's original constraint (repo-root
dogfood copies must stay put) the brief's primary proposed gate — "`render-hooks plan:post` no
longer emits the collision warning" — was **unsatisfiable**, so this plan fell back to a static
packaging-scope proof. **That constraint has since been reversed by explicit user direction**
(see "Repo-Level Duplication Removal" below): the colliding project-scope copies are now
deleted, so the collision warning **is** expected to disappear and the brief's original gate
becomes satisfiable — but **it is not an unqualified win**, and Task 3 asserts it only in the
`ponytail` case plus whichever disposition Task 0 selects. Removing the collision *re-enables*
the `sota-numerics` blocking gate, which then fails closed on a missing script path (finding 6
below). The warning disappearing and the repo still planning successfully are two different
properties; assert both or neither.

The causal chain above still holds and is the reason the gate now works: `overlayRoots` scans
the project **directory** `<projectRoot>/.gsd/capabilities`, not the `.gsd-capabilities.json`
registry. (Corroborating evidence: `sota-numerics` has no entry in `.gsd-capabilities.json` at
all, yet its collision fires — so the directory scan, not the manifest, is what creates the
duplicate registration. Confidence: 95.) Deleting the two directories empties the project
overlay of those ids, leaving only the global registration, which is already the copy that
actually renders the live gate.

**The packaging defect remains a genuinely separate defect** from the duplication, and both are
fixed here. Scoping `source` fixes what gets *published to consumers*; deleting the duplicates

## Alternatives Considered

- **Scoped plugin subdirectory (`source: "./plugins/beads-lifecycle"`) — CHOSEN.** The
  marketplace schema resolves a plugin `source` string relative to the marketplace repo root
  and accepts any subdirectory, with the plugin's own `.claude-plugin/plugin.json` at that
  subdirectory's root; see Anthropic's plugin-marketplace reference at
  https://docs.claude.com/en/docs/claude-code/plugin-marketplaces (2026). Cost is one
  `git mv` set plus one JSON string; the exclusion then holds by construction — no filter to
  keep in sync, nothing to forget when a fourth capability is added. Verifiable statically by
  `claude plugin validate --strict` against the new root, which is why it is also the
  cheapest to audit.
- **Publish-step filter that prunes `.gsd/capabilities/` to owned ids** (the ticket's own
  suggestion, `.planning/` bd ticket `gsd-beads-1iq`, 2026). Rejected: it only sanitizes the
  release-archive path, so `claude plugin install` from the marketplace — which clones and
  roots at `source`, bypassing any release step — stays broken. It also adds a script whose
  allowlist must be updated for every new capability, i.e. more LOC and a standing
  maintenance obligation, to fix strictly less.
- **Exclude via `.gitignore` / an allowlist field in `plugin.json`.** Rejected on ecosystem
  grounds: `plugin.json`'s documented schema at
  https://docs.claude.com/en/docs/claude-code/plugins-reference (2026) exposes no file
  allowlist, and `.gitignore` cannot be used since the dogfood copies must stay **tracked**
  for this repo's own lifecycle. Non-mechanism.
- **Status quo — keep `source: "./"`, rely on `session-start.sh` only ever installing
  `beads`.** Rejected: leaves the published release archive shipping foreign bundles
  (`.github/workflows/release.yml`, 2026), leaves README:106's contents claim false, and
  makes a one-literal edit in a hook the only thing preventing a real fail-open.

Decided by: simplicity/LOC — the chosen mechanism is a directory move plus a one-string
manifest edit that makes the exclusion structural, versus a filter script that must be
maintained per-capability and still fails to cover the marketplace-install path.

**Note on scope of this comparison.** The four alternatives above weigh *packaging-scope*
mechanisms against each other and that comparison stands unchanged. The repo-level deletion of
`.gsd/capabilities/{sota-numerics,ponytail}/` is **not a fifth alternative to them** — it is a
separate, additional, user-mandated fix layered on top of the chosen one. The two address
different defects (what gets published to consumers vs. what the repo contains) and neither
substitutes for the other: scoping `source` alone would leave the duplicates in the repo, and
deleting the duplicates alone would leave `source: "./"` still rooting the plugin at the whole
monorepo and still shipping `.planning/` and `.beads/`. The deletion itself had no alternatives
to weigh — the user specified the outcome directly, and the only mechanism question (`git rm -r`
vs. history rewrite) is settled by the recoverability requirement.
