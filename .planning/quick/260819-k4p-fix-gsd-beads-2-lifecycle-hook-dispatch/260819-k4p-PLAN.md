# Quick Task: make the four dead lifecycle hooks dispatch

## Plan Header

- **Mechanism:** A plugin `PostToolUse` hook matches the `gsd_run loop render-hooks <point> --raw`
  Bash call gsd-core **already makes** at every dead point, and runs the matching `sync.py` verb
  itself. Dispatch becomes a deterministic script run by the harness, not prose an LLM must obey.
- **Forbidden:** New marker-bracketed prose patches into `plan-phase.md` / `execute-phase.md`;
  any dispatch path that depends on gsd-core workflow prose; any hook exit code that can fail a
  tool call; duplicating phase-resolution or bd logic that `sync.py` already has.
- **Audit:** `sync.py` unit tests drive `lifecycle_dispatch` against a real temp project tree with
  a stubbed `bd` on PATH — asserting the *observable* effect (issues created, `beads_epic` written,
  `BEADS.md` regenerated), never that a function was called. A shell smoke test feeds the hook a
  real `PostToolUse` payload and asserts the sync.py invocation happens for a matching command and
  does not for a non-matching one.

## Problem (github.com/davdittrich/gsd-beads#2)

`capability.json` declares six `kind: "step"` hooks. Verified against installed gsd-core 1.10.0:

| Point | Dispatch site | What is actually there | Fires? |
|---|---|---|---|
| `plan:pre` | `plan-phase.md:441` | Generic step contract, but §5.6 Branch 2 returns when `frontend == false` and Branch 5 needs `AUTO_CHAIN` | No (manual mode) |
| `plan:post` | `plan-phase.md:1355` | `kind == "gate"` only; also short-circuits when `gap-analysis` is inactive | No |
| `execute:wave:pre` | `execute-phase.md:647` | Renders JSON, then checks only for a *contribution* | No |
| `execute:wave:post` | `execute-phase.md:1016` | `kind == "gate"` only | No |
| `verify:post` | `execute-phase.md:1202` | Step loop hardcoded to `ref.skill == "secure-phase"` | No |
| `ship:pre` | `ship.md:226` | Generic step loop — installed by this capability's own patch | Yes |

Failure is silent: every hook is `onError: "skip"`, so a phase plans and executes with zero bd
issues and nothing reports it.

Secondary: the patch-loss detector (`beads-recall` Step 3.5) sits at `plan:pre` — itself one of the
dead points — so it shares the failure mode of the thing it protects.

## Alternatives Considered

| Approach | Performance / LOC | Simplicity | Ecosystem | Maintenance | Verdict |
|---|---|---|---|---|---|
| **PostToolUse hook drives `sync.py`** (chosen) | ~1 shell file + 1 argparse verb; no gsd-core writes | Deterministic script; matches a call gsd-core already makes | Claude Code hook API; repo already ships `.codex`/`.cursor` hook variants | Immune to gsd-core updates — gsd-core would have to stop calling `render-hooks` at all | **Chosen** |
| Two more prose patches in `GSD-CORE-PATCH.md` (issue's literal suggestion) | 4 patches × ~40 lines of prose into someone else's files | Dispatch still depends on an LLM reading and obeying prose | — | Every gsd-core update can silently strip them; detector is itself broken | Rejected — the issue's own text calls this "treating a symptom that keeps recurring per capability" |
| Auto-apply the patches from `capability-auto-install.sh` | Same patch content + ~30 lines of idempotent insertion | Self-heals patch loss | — | Plugin writes into `~/.claude/gsd-core/workflows/*.md` unattended; anchor drift on a gsd-core update degrades to a warning | Rejected — fixes *patch loss*, not *prose-dependent dispatch* |
| Upstream gsd-core change (generic `kind == "step"` dispatch at every point) | Smallest possible | Correct fix | Tracked as `open-gsd/gsd-core#3554` for `ship:pre` | Not shippable from this repo | Complementary, not a substitute |

**Why the chosen mechanism wins on the ranked criteria:** it is the only option whose dispatch is
*mechanical* (rank 1 — a hook the harness runs, not a paragraph a model may skip), it removes rather
than adds patched files (rank 2), and it cannot be silently dropped by a gsd-core update (rank 4).

## Point → operation mapping

Every operation is derivable from `phase_dir` alone, so no wave plan-id list is needed:

| Point | Existing `sync.py` verb |
|---|---|
| `plan:pre` | `beads_recall` + `check_shipmd_patch` + `check_execute_plan_patch` |
| `plan:post` | `create_issues` for each `phase_dir/*-PLAN.md` |
| `execute:wave:pre` | `render_wave_status_block` over every plan id in the phase |
| `execute:wave:post` | `reconcile_stale_closed` (phase-wide idempotent backstop, D-08) |
| `verify:post` | `regenerate_beads_md` |
| `ship:pre` | untouched — already dispatched by this capability's `ship.md` patch |

## Known limits

- **`execute:wave:pre` emits a phase-wide `<beads_status>` block, not a wave-scoped one.** The
  render-hooks Bash call carries no wave plan-id list. Phase-wide is a superset, so no pointer is
  lost; it is just less targeted than the `ship:pre` patch path.
- **Claude Code only.** `runtimeCompat.supported` is `["*"]`, but `PostToolUse` is a Claude Code
  hook. Other runtimes keep the pre-fix behaviour (`ship:pre` only). `.codex/hooks.json` and
  `.cursor/hooks.json` already establish the per-runtime hook pattern for a later pass.
